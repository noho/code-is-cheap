## 1. Goal、scope 与 review question

用户已确认的 goal 是：九条既有 managed third-party shim routes 全部修复；对 Kimi 要真实完成 native initial task、同一 child follow-up、child 读取未知无害文件；不得 catalog/provider fallback，不得削弱 policy；在 live sync 前不得 sync/restart，也不得向原业务 parent thread 发技术 callback。

目标 plan 的方向是：仅 Kimi route 默认关闭的显式 route flag，请求展开 function-only namespace，响应在 `response.output_item.added/done`、`response.completed.response.output[]` 和普通 JSON `output[]` 中按请求内 map 恢复 namespace；不引入 alias、跨请求状态、catalog/v2 强制迁移或完整 stream buffering。

本 review 集中回答 controller 指定的核心问题：**是否为 native agent goal 真的需要展开所有 MCP/其它 namespace，还是应只展开/恢复实际 native collaboration namespace；以及该设计是否足够正确、最小、可验证。**

## 3. Findings

### 1-未修复-[高]-建议方案把所有 function-only namespace 展开/恢复，超出 Kimi native collaboration 目标，并引入无关 MCP 工具能力扩张与冲突拒绝（accepted-candidate）

- **位置**: `kimi-namespace-plan.md` §建议的最小生产方案 §边界和请求不变量 2-5；§一次 targeted 原生 prototype 的请求 1；§实现后需要的回归与原生证据
- **问题类型**: 过度设计 / 目标漂移 / 范围漂移 / 安全边界
- **当前写法**: “适配只针对 `/responses` 的顶层 `tools` 中已知 function-only namespace wrapper”，“全部 callable 名称必须可证明全局唯一，包括原平铺 function/custom 与 namespace 内 function”；prototype 实际展开了 `multi_agent_v1`、`mcp__github`、`mcp__node_repl` 三个 namespace，并保留全部函数名。
- **反例/失败场景**:
  1. 用户的 Kimi session 有两个 MCP server 同时暴露 `search`、`read_file` 之类的通用名。plan 的“全局唯一”规则会在发 upstream 前把整个请求 sanitized400，即使 `spawn_agent` 本身唯一、native subagent 完全可用。native goal 被一个与它无关的 MCP 命名冲突阻塞。
  2. 由于 request flattening 使原先 namespace-wrapped 的 MCP functions 变成平铺 callable，Kimi 现在可以实际调用这些函数；这不是 native spawn/wait/child-read 所需，且 plan 自己在响应规则中写明“不能据此扩充可执行工具集”。该能力扩张会让普通 Kimi session 出现此前不可发生的 MCP 调用（包括写操作），超出用户确认的目标。
  3. 目标 plan 没有给出“哪些 namespace 属于已知”“何时应展开”的确定集合；实现者可能把“已知 function-only”理解为所有当前 namespace wrapper，从而把无关 MCP 全部纳入；也可能自行猜测前缀/白名单，产生不可审查的行为差异。
- **为什么有问题**: 已证实的 native 失败只涉及 `multi_agent_v1/spawn_agent`，而 parent 只需要 spawn/wait，child file read 使用平铺 `exec_command`。`mcp__github`/`mcp__node_repl` 既不是 failure cause，也不是 goal 的必要路径；把它们纳入适配是把“Kimi namespace compatibility”扩大成“Kimi 全 MCP 工具兼容”，增加无关 schema、冲突和 tool-surface 风险。controller 也明确要求不要把 full MCP support 作为新 goal。
- **直接证据**:
  - `evidence/kimi-namespace-diagnostic/routing-verdict.json`: `name="spawn_agent"`、`routing_result="FAIL: unsupported call: spawn_agent"`、`child_created=false`。
  - `evidence/kimi-namespace-diagnostic/attempt-1/namespace-transform.json`: `expanded_count=3`，`mcp__github` 25 个 function names、`mcp__node_repl` 3 个；`multi_agent_v1` 是唯一 native collaboration namespace。
  - `evidence/kimi-namespace-diagnostic/attempt-1/wire.json`: `native_descriptors` 中 `exec_command` 是平铺 function，`multi_agent_v1` 是 namespace；没有证据表明 MCP namespace 是 native goal 依赖。
  - `evidence/kimi-namespace-diagnostic/codex-routing-source.json`: `registry.rs::registered_tool` 按完整 `ToolName` 查表；`spawn.rs::tool_name` 注册 `multi_agent_v1/spawn_agent`；`tool_name.rs` 把空 namespace 归为 `functions`。
  - `evidence/kimi-namespace-diagnostic/kimi-tool-namespace-diagnostic.json`: namespace-wrapped `probe_echo` 返回 completed 但 `output=[]`；flat `probe_echo` 返回实际 `function_call`。这直接证明 flattening 会让工具变得可调用。
  - `kimi-namespace-plan.md:83` 自己要求“不能据此扩充可执行工具集”，与 request 侧无差别展开 MCP 相冲突。
- **影响**: 真实 Kimi session 可能因无关 MCP 重名被 400；Kimi 的 callable tool surface 被无意扩大；实现和测试面扩大到 MCP schema/语义；review 难以证明没有误路由或非目标工具执行；与用户“只修 native subagent”的目标不一致。
- **建议改法和验证点**:
  1. 把 request flatten 与 response restore 限定为 **实际 advertised 且 native collaboration 所需的 namespace**；当前直接证据只有 `multi_agent_v1`。`collaboration` 只有在 Kimi 实际 descriptors 中出现且 spawn/follow-up/child-read 确实依赖时才纳入，不预置未来 namespace。
  2. 所有其它 namespace（包括 `mcp__github`、`mcp__node_repl`）保持原始 bytes/shape 透传，不参与 flatten，也不参与全局唯一性拒绝。
  3. request-local map 只包含被展开的 native functions；唯一性检查只覆盖这些 native names 与平铺 function/custom names，以及 native names 之间；冲突仍 fail closed 400。这样保留“恢复名全局唯一、不会误路由”，但不会因为无关 MCP 重名阻塞。
  4. targeted revalidation 改为只 flatten `multi_agent_v1`（以及实测必需的 native namespace），确认 Kimi 仍产生裸 `spawn_agent`，恢复后 native spawn/wait/child turn 成功；若失败，保留证据再讨论是否确有 wider adapter counterexample。当前没有这种 counterexample。
  5. 增加回归：无关 MCP namespace 即使内部重名也保持 passthrough 且不 400；native names 仍恢复；未显式 flatten 的 MCP 函数不会因本适配变为 callable。
- **修复风险（低/中/高）**: 低-中（改动是将泛化适配收窄到已证实范围，不改变 response 恢复的核心机制）
- **严重程度**: 高

### 2-未修复-[中]-“用户明确要求本轮不实现 stateful stream rewrite”归因错误，可能把必要的 request-local SSE 兼容排除出实现范围（accepted-candidate）

- **位置**: `kimi-namespace-plan.md:89`（§建议的最小生产方案结尾）及 §当前交付和阻塞
- **问题类型**: 动机不成立 / 归因错误 / 范围漂移
- **当前写法**: “用户明确要求本轮不实现 stateful stream rewrite，故这里仅给设计，代码仍未改。”
- **反例/失败场景**: controller 或实现者按字面理解，把 response namespace restoration（裸 `spawn_agent` 能被 Codex 路由的唯一必要步骤）视为用户禁止的“stateful stream rewrite”而推迟或省略；Kimi native child 继续阻塞。或者相反，把该句当作 scope 授权而引入不必要的跨请求状态。
- **为什么有问题**: 用户实际约束是 live sync/restart 前不得部署、不得向原业务 parent thread 发技术 callback；本 diagnosis delegate 未获生产实现授权，所以本轮只写设计。用户没有禁止 all-provider repair 所需的 request-local response compatibility。plan 自己提出的 response restoration 正是 request-local SSE 兼容，不是 cross-session stateful bridge；把它归因成用户禁令会误导后续 gate。
- **直接证据**: `control.md` 的 authorization boundary 明确“shim source has not been deployed/restarted”“prohibits technical callback”，并授权本扩展；`kimi-namespace-plan.md` 自身 §响应的最小恢复设计提出 added/done/completed/JSON 恢复；用户本次明确说明“userdidn't prohibit necessary request-local SSE compatibility within all-provider repair goal”。没有用户禁止 request-local SSE 的证据。
- **影响**: implementation 被错误缩 scope；plan 自相矛盾；Kimi 仍无法完成 native goal；review/closeout 可能把未实现的核心响应契约当作已 defer 的 future work。
- **建议改法和验证点**: 改成精确表述：“本 diagnosis delegate 未获生产实现授权，故本轮未改代码；response namespace restoration 属于 all-provider repair 的必要 request-local compatibility，经 controller/plan review 批准后可实现；仍不引入跨请求 state/alias，不改变 no live sync/restart/callback 约束。” 同时保留 plan 的 no cross-request state 设计。
- **修复风险（低/中/高）**: 低
- **严重程度**: 中

## 4. Open questions

1. **Namespaced history acceptance**：下一请求携带恢复后的 namespaced `function_call` history 时，Kimi gateway 是否接受？plan 已安排 targeted revalidation；若失败，需要什么最小契约调整应由 controller 基于新证据裁决，不能预设删除 history namespace。Owner: controller/implementation；destination: `evidence/kimi-namespace-diagnostic` targeted revalidation。
2. **Guardian 请求路径**：`namespace_function_compat` 是 route-wide；plan 只明确保留 guardian buffering/retry，没有说明 `codex-auto-review` guardian 请求是否也做 request flatten/response restore。若 guardian 请求包含 namespace wrapper 或未知 shape，可能出现 400 或行为变化。应在实现前明确“apply 或 bypass”，并用实际 guardian 请求形状做离线测试。Owner: implementation；destination: response/request offline tests。
3. **Ordinary streaming 即时性与并发隔离**：plan 要求“继续真正流式发送”，并声明 map 为每请求一份；测试清单有 parallel interleave，但未明确断言首个相关 event 在上游完成前送达下游，也未明确并发两个请求使用彼此独立的 map。建议补 focused tests（gate 上游分块、first-event flush；两个并发请求不同 tools/map）。Owner: implementation；destination: offline response tests。
4. **Response compression/header 真实边界**：原型观察到可解析 SSE，但 production ordinary streaming 当前直接透传原始 bytes；应证明实际 Kimi 响应编码是 identity/gzip/deflate，未知编码 fail closed 且不会把压缩字节当已修复。Owner: implementation；destination: targeted observer/validation。
5. **Structured `tool_choice` 与中性形态**：实际只观察到 `auto`；plan 明确 structured namespaced function 400，但应补 absent/auto/none/required 与 structured flat/native 的回归，避免把合法 flat choice 误拒。Owner: implementation；destination: request offline tests。
6. **Mid-stream 冲突/abort 语义**：若 added 已转发后 done/completed 出现显式冲突（包括显式 `functions` 或其它 namespace 与请求内 map 冲突），adapter 不能发 HTTP 400；应明确 close 还是 `response.failed`，并确保 client 不会执行半恢复的 function_call。Owner: implementation/code review；destination: response error-path tests。
7. **`additional_tools` / compaction**：plan 已 defer `additional_tools`；若实际 native follow-up 或 context compaction 路径依赖它，需要新证据和最小扩展。Owner: controller；destination: 后续 work unit（非当前 blocker）。
8. **当前矩阵表述**：plan 文中“6/9”与当前 controller 证据（7 strict、MiMo Flash partial、Kimi blocked）不一致。它不影响 Kimi 设计，但 closeout 必须使用最新实测，不能把 plan 的旧计数带入 PR/closeout。Owner: controller。
9. **Production outbound observability**：plan 只规定 evidence hashes 与 sanitized protocol error；未规定生产日志如何报告 flatten/restore 次数、冲突/unknown shape/parse failure，且不能泄漏 prompt、tool arguments 或私有连接。建议定义 sanitized counters/log（route、flag、flattened namespace names/count、restored call count、error class），并纳入离线测试/code review。Owner: implementation；destination: offline log tests / code review。

## 5. Residual risks and suggested tracking destination

- **若保留广泛 flattening**：无关 MCP 冲突 400、callable tool surface 扩张、非目标工具执行风险。Destination: Finding 1 / plan revision；owner: controller。
- **Gateway 拒绝 namespaced history**：native follow-up 的核心未知；targeted revalidation 是 gate；若失败，保留证据后由 controller 决定最小契约调整。Owner: controller/implementation。
- **Guardian/auto-review 与 route-wide flag 交互**：可能 fail closed 或行为变化；destination: offline guardian test；owner: implementation。
- **Unknown response encoding / compression**：可能无法解析或错误地“修复”；destination: targeted production-boundary evidence + fail-closed logging；owner: implementation。
- **Streaming latency regression**：若实现整段 buffering，native probe 仍可能通过但普通 streaming 退化；destination: first-event immediacy test；owner: implementation。
- **Production observability 缺口**：若只记录成功/失败而无可审查的 sanitized flatten/restore/error 计数，runtime 失败难定位；destination: offline log tests + code review；owner: implementation。
- **`additional_tools` / compaction**：本次未覆盖；destination: future work unit with actual native evidence；owner: controller。
- **未来 namespace metadata / tool shape**：plan 选择 fail closed 400，是安全但可能影响未来 Kimi 兼容性；destination: maintainer compatibility follow-up。
- **全局矩阵状态**：7 strict / MiMo Flash partial / Kimi blocked；destination: controller closeout，使用当前证据替换 plan 内旧计数。

## 6. Final conclusion

**fail**（需修订后再进入 implementation）。

核心诊断成立：request-only flattening 确实产生裸 `spawn_agent`，而 Codex 0.167 按完整 `ToolNamespace` 路由，因此 response namespace restoration 是必要方向；plan 对 SSE/JSON、request-local map、冲突 fail-closed、no alias/no cross-request state 的总体方向也合理。

但当前“最小生产方案”并不最小：它把 flatten/restore 扩大到所有 function-only namespace（prototype 实际包含 `mcp__github`、`mcp__node_repl`），并以全局唯一性规则把无关 MCP 重名升级为整请求 400，同时扩大了 Kimi 的 callable tool surface。现有证据只支持 native collaboration namespace（当前为 `multi_agent_v1`）；没有 counterexample 表明 MCP namespace 是 native spawn/wait/child-read 的必要条件。应将适配收窄到实际 native collaboration namespace，其他 namespace 精确透传，并只对恢复名做唯一性检查。另需修正“用户明确要求本轮不实现 stateful stream rewrite”的归因错误，明确本轮只是 diagnosis delegate 未获生产实现授权，request-local SSE compatibility 仍在 all-provider repair goal 内。

修订上述两点后，plan 可在处理 Open Questions（尤其 namespaced history、guardian、immediacy/concurrency tests）后进入实现与验证。本轮未执行任何 native/vendor 探测、broad suite、生产修改、stage/commit/push/deploy 或消息发送。
