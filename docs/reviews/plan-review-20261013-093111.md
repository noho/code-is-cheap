## Special lenses 应用结果

- **Goal-bound minimal design**：每个 decision/slice/验收均直接映射 G1–G6 或 goal 授权的 docs decision。
  plan 把“将来不同文案/uppercase UUID/预算变化”“服务端根因”“历史业务覆盖”“live 无法断流”全部放入
  residual risks（later work unit），未升级为新目标或新验收。**无 goal drift。**
- **Architecture boundary**：变更收敛在 collector 的单一识别函数；runner、schema、state machine、
  provider/model 配置、权限边界均不动；D2 重述的不变量与所有权（collector 负责机械分类、业务验收责任外置）
  与既有分层一致。**无跨层泄漏。**
- **Best-practice**：fail-closed（未知/近似/未证明一律 fatal）、测试独立 oracle、保留原诊断不覆写、
  baseline 与修复验证分离、C1 部署前 ownership 核查——均为该问题类型的正确实践，且符合仓库既有约定。
- **Optimal-solution**：候选方案中（放宽为任意 `Reconnecting` 前缀 / runner 层拦截 / 请求 ID 跨事件关联 /
  通用服务器错误 taxonomy），精确第二文案白名单 + 既有恢复队列是满足 goal 显式约束（“不能固定为两个历史
  request ID，也不能泛化成任意服务器 error”）的最小正确路径。**无更优未采纳路径。**
- **Overengineering**：plan 明确拒绝 retry 执行器、序号递增/唯一性/总条数约束、UUID 语义关联、通用解析机制；
  测试 seam 为 optional 且默认保持旧行为。**无过度设计。**
- **Overcoupling**：matcher、测试、README 段三者可独立评审与回滚；新通知复用既有单一队列与 finalize 是
  领域语义（同一恢复证明）而非不当绑定；future-slice 未被当前结构锁死。**无过度耦合。**
