## Assumptions tested（逐条证伪尝试）

1. **「ENOENT-only 容忍必须自研 helper」** — 部分证伪：本机 Homebrew 3.11.15（posixpath.py:38/428）与 uv 3.12.12 均含回补的 `os.path.ALLOW_MISSING`，且矩阵显示它与计划候选解析在 10 用例中 9 个一致；唯一功能分歧恰在 `x/../y`（x 非目录）——ALLOW_MISSING 按词法接受，计划候选按内核语义 ENOTDIR fail-closed。结合 README:112 只承诺 “Python 3.11+”（不承诺补丁级 backport）、goal 排除 compatibility 层，自研 helper 仍是正确取舍，但计划的论证未引用自有矩阵证据（Finding 2）。
2. **「自定义解析器语义 = 内核语义」** — 部分证伪：对「先 ENOENT 再 `..` 后 ENOTDIR」用例，内核实测为 ENOENT（缺组件即停），计划候选判 ENOTDIR fail-closed；对「`x/../y` 全存在链」内核判 ENOTDIR 而现状 `resolve(strict=True)` 接受。契约比内核更严/更紧的两处转变未披露（Finding 1）。
3. **「不扩大权限」** — 通过：新增项只进 denyRead/denyWrite；srt 把 `{path, literal:true}` 编译为 subpath+literal 祖先 deny（profile 实测），launcher 压缩只做等价 union；无任何 allow 增加。
4. **「两轮 verify 不会伪接受不存在目标」** — 通过（设计推演+证据）：ENOENT 例外要求 (a) metadata 登记并通过 lexical/canonical 与包含性校验、(b) `ancestor ∈ verified_existing`（第一轮真实 query=True + 实际 PermissionError）、(c) target query=True（弱一致性检查）、(d) 实际 open/listdir 返回 ENOENT；任一缺失即拒绝。首次出现即拒绝的路径（query=False、ancestor ENOENT/读取成功、manifest 缺字段）均由 §7 测试矩阵覆盖。未找到“跳过真实验证仍被接受”的组合。
5. **「ancestor = 最近已存在目录」必然可列举、可预读** — 通过：解析器保证 existing 前缀均为目录，父链首个 existing 节点为目录；ancestor 进入现有 pending 扫描（预列举 + 有效目标扩展 + hardlink/special 拒收，无旁路）。`/` 即时拒绝、扫描失败 fail-closed。
6. **「valid symlink/hardlink/FIFO 语义保留」** — 通过：现有 `tests/test_agent_sandbox.py` 的 alias/hardlink/FIFO/Seatbelt 假证明用例映射进 plan §7 保留断言；缺失目标不预读、FIFO 目标仍在打开前拒收；对“目录内未扩展 special-file”的一般化强化明确留作非目标。
7. **「无循环/无 pending 不稳」** — 通过：visited 按 canonical path 去重（新增 ancestor 再含原目录不再入队）；循环按解析栈（非全局）检测，ELOOP/递归耗尽 fail-closed；missing 元数据重复 key 保留首次来源。
8. **「报告可定位失败」** — 通过（契约设计）：missing→ancestor 扩展逐条 stderr 报告 + 既有冲突错误；ancestor 扫描中的失败经 pending 上下文（declared/link/raw_target/ancestor/errno）包装为 ValueError；顶层仍 exit=1 无 runner。见 Finding 1 中对“解析跨越缺失组件但终态存在”这一无报告路径的保留意见。
9. **「单一 slice 与最小实现」** — 通过：改动封闭在 `scripts/agent-sandbox`（load_denies/verify/main/report）、`tests/test_agent_sandbox.py`、README EN/ZH、advanced.md；launcher/srt/installer/runner/lifecycle 不改；未发现 goal drift、未授权依赖升级或一般化框架（helper+metadata 不构成 compatibility 框架）。

## 重点区域评估（对照总控 focus）

- **扩大 deny 但不 grant 权限的副作用**: 无权限增加；副作用集中在“连带拒绝”。生产语义上新增两类连带：ancestor 子树（含 siblings）+ 词法重入的既有目标（Finding 1-B）。ancestor 若与 required input/write root/输出/state/probe 冲突，现有检查在 runner/srt 启动前拒绝并可定位；否则运行时位于 ancestor 下的非必需资源会被静默拒绝（已列 residual，docs 需明示）。
- **原 required inputs/工具冲突定位**: 成立。`main` 先报告扩展再执行 `require_readable`/write/输出检查；`--check` 亦报告但不宣称 kernel verified。测试清单包含“ancestor 含 required input → 无 runner 标记 + 扩展报告 + 既有冲突错误”。
- **declared 有效输入、valid symlink 目标扩展**: 保留（声明路径仍必须存在；外部有效目录继续递归扫描与二级 link 扩展；hardlink/FIFO 在打开前拒收）。但解析契约对“全存在链”的接受边界相对现状收紧（Finding 1-A），与 goal 成功信号 “Preserve valid symlink handling” 存在字面上需要裁定的交集。
- **hardlink/FIFO 语义**: anchor 扫描若遇到 hardlink/特殊扩展目标 → 上下文拒绝（fail-closed，新触发面已在 plan §3/§4.2 声明）；缺失目标本身不预读、不进 pending；无新特殊文件策略。
- **两轮 verify 不能伪接受不存在目标**: 见 assumption 4；设计闭合，未发现偷渡路径。
- **循环/权限/ENOTDIR**: 覆盖完整（含自环/双节点环、EACCES 注入、ENOTDIR、ENOENT→`..`→ENOTDIR、尾 slash 指向文件）；全部不得转成 missing。`missing-then-enotdir` 判 ENOTDIR 与内核 ENOENT 的差异见 Finding 1。
- **ancestor 扫描与已有 visited 稳定性**: visited/去重/`exact 保留` 规则组合可终止且确定性；级联（新 ancestor 内再发现 dangling link 推高 ancestor）未在 plan 中声明，列为 Open Question。
- **单 slice 与最小实现**: 解析、策略集合、验证例外共同构成一条可执行契约，拆分反而产生中间不一致——同意单 slice 判定；allowed files 封闭清晰。
- **ALLOW_MISSING 减负挑战**: 本机可近似替代（9/10 用例一致），但以合同可用性、补丁级语义漂移与 `x/../y` 静默接受为代价；goal 排除 compat 层 ⇒ 保留 helper 正确，但需补齐排除论证与语义钉死（Finding 2）。不建议引入 `hasattr` 双路径。

### 1-未修复-中-解析契约相对现状引入两处未披露的行为转变（一处收紧可启动配置、一处静默扩大 deny），无文档、无测试、无报告

- **位置**: plan §4.1 规则 2/3/5（算法契约）、§7 Setup/resolution 测试清单、§8 docs decision；现状代码 `scripts/agent-sandbox:78`（`entry.resolve(strict=True)`）。
- **问题类型**: 契约缺失 / 行为转变未声明（与 goal 成功信号 “Preserve valid symlink handling” 的边界需要裁定）。
- **当前写法**: 规则 2「在处理下一实际组件、`.`、`..` 前，若当前前缀已存在，必须是 directory，否则 ENOTDIR」（无条件）；规则 3「缺失则保留组件并继续后续解析…缺失后的 `..` 可能重新进入存在区域」；规则 5「中途曾 ENOENT、最终重新到达存在目标时，按存在目标处理」。
- **反例/失败场景**（三例，均有直接证据）:
  - **A（收紧）**: 禁读目录内 `link -> ../plain/../good/data`（`plain` 为普通文件、`good/data` 存在）。现状：`resolve(strict=True)` 成功 → 接受并把 `good/data` 加 deny → **setup 可启动**。新契约：处理 `..` 前 `plain` 非目录 → ENOTDIR → **setup 带上下文拒绝**。内核实测（via-link 与 target-text）确为 ENOTDIR，fail-closed 方向安全，但配置从可启动变不可启动，未经声明。
  - **B（放宽 + 静默过度 deny）**: 禁读目录内 `link -> ../anchor/missing/../../otherdir/config`（`missing` 缺失、`otherdir/config` 存在）。现状：strict resolve 抛 FileNotFoundError → setup 失败（本 bug 类）。新契约：最终到达存在目标 → 按现有目标处理 → 把**声明目录之外、与链路无实际可达关系的既有文件** `otherdir/config` 加入 denyRead/denyWrite（并要求其预先可读）。该事件不产生 `missing_targets` 元数据，§4.3.1 的 stderr 报告只覆盖 missing 元数据 → **完全无报告**。
  - **C（与内核不一致的判定）**: `link -> ../anchor/missing/../../plain/child`。内核实测 ENOENT（缺组件即停）；契约判 ENOTDIR fail-closed。与 goal「非 absence 错误不得当 missing」方向一致，但这是契约自身的词法续解模型产物，docs 未说明。
- **为什么有问题**: 实现者严格照 §4.1 实施会在实现中出现两类未申报副作用：把现状可启动配置变为拒绝（A），和把无关既有文件静默纳入 deny、无任何可观测痕迹（B）；review/验收无法区分“有意的内核精确语义”与“实现偏差”，且目标成功信号中 “Preserve valid symlink handling” 的解释权被默认交给实现者。
- **直接证据**: `resolution-matrix-raw.json`：`enotdir-before-parent` strict=success（`…/good/data`）/ candidate=NotADirectoryError；`after-missing-parent` strict=FileNotFoundError / candidate=success，且 `assert-evidence.py:39` 断言其路径等于 `valid` 用例路径；我的独立实验（/private/tmp/claude-501/planreview-dangling-check）：strict_resolve=success、kernel open via link=ENOTDIR(errno 20)、target-text=ENOTDIR；`missing-then-enotdir` kernel=ENOENT vs candidate=NotADirectoryError；plan §7 未列 A/B 用例，§8 未提行为转变。
- **影响**: 实施 Agent 生成未申报的接受边界变化；旧配置启动失败无迁移说明；无关文件被静默 deny 导致运行期排障困难（“文件明明在，runner 却读不到”）；plan review/deepreview 需返工裁定。
- **建议改法和验证点**:
  1) 在 §4.1/§8 以“相对现状的行为转变”条目显式列出 A/B/C 及理由（A/C：内核精确 fail-closed；B：词法续解的保守覆盖），并写进 README/advanced 的同一段落（accepted 语义的文档化义务）；
  2) §7 增补 focused 用例：A（无 missing 组件的 `x/../y` → ValueError 带失败组件/errno）；B（返回 existing target、deny 含该 target、且对该“跨越缺失组件的重入”给出 stderr/报告——若 controller 决定接受静默，则在 docs 明示）；C（确认 fail-closed 且错误文案说明原因）；
  3) 二选一的语义裁定（见 Open Question 2）：保留内核精确 fail-closed（推荐，需 1+2 落地）或对“不含 missing 组件的链”采用既存 strict resolve fast path 以保持现状接受边界（需两路径测试，并说明其保留 Python/内核分歧）。

### 2-未修复-低-自定义解析器相对 os.path.realpath(ALLOW_MISSING) 的取舍论证缺少自有证据与显式排除，存在实施期被“简化”回去的漂移风险

- **位置**: plan §2 末段与 §4.1（helper 必要性论证）；证据在 `resolution-matrix-raw.json` 的 `stdlib_allow_missing` 列（计划自己采集却未引用）。
- **问题类型**: 非最优方案论证缺口 / 可实施性（防止实现期重新设计）。
- **当前写法**: 「本机 3.11.15 已有回补的 os.path.ALLOW_MISSING，但不能假设所有受支持的 3.11 都有这个 API，也不改变 Python 版本下限。直接 `resolve(strict=False)` 会掩盖 EACCES/ENOTDIR；在第一次 ENOENT 后直接拼接剩余字符串，也会漏掉后续 `..`…需要一个仅用于本入口的、只容忍 ENOENT 的小解析 helper。」
- **反例/失败场景**: 实施者看到本机 ALLOW_MISSING 可用、矩阵 9/10 用例与候选一致，直接把 helper 替换为 `os.path.realpath(p, strict=os.path.ALLOW_MISSING)`（或加 `hasattr` fallback）→ (i) README 只承诺 Python 3.11+，部分补丁级解释器（该 API 为 3.13 引入并回补，非全量 3.11/3.12 补丁）直接 AttributeError 或语义分叉；(ii) `x/../y` 用例被静默接受，与 plan 自身“ENOTDIR fail closed”契约冲突（矩阵已记录该分歧，`strict`/`nonstrict`/`candidate` 三列中仅 `stdlib_allow_missing` 出现 success）；(iii) fallback 双路径即 goal 明确排除的 compatibility 层。
- **为什么有问题**: 该 helper 是本修复的安全核心之一；“为什么不用 stdlib”的论证只覆盖了 `strict=False` 的遮挡问题，未覆盖最接近的替代 API 自身；契约不完整会让后续 review/实现围绕同一点反复，或静默选择更宽松语义。
- **直接证据**: 矩阵 `stdlib_allow_missing`：与 candidate 一致的用例（missing-leaf/ancestor/relative/chain/valid/after-missing-parent 同路径；loop=OSError ELOOP；permission=PermissionError errno 13；enotdir/missing-then-enotdir 同类错误）之外的唯一功能分歧为 `enotdir-before-parent`（success vs NotADirectoryError）；可用性：Homebrew 3.11.15 posixpath.py:38/428 有、uv 3.12.12 有、`/usr/bin/python3` 3.9.6 无（低于合同下限）、README:112 无补丁级承诺；goal 非目标“compatibility/migration layer”。
- **影响**: 安全边界语义随解释器补丁级漂移；实现返工或 review 拉锯。
- **建议改法和验证点**: 在 §2/§4.1 增加一段“为何不用 realpath(ALLOW_MISSING)：合同下限不保证 + 本矩阵已证 `x/../y` 分歧（引用 `enotdir-before-parent` 行）+ 明确拒绝 hasattr 双路径（属 compat 层）”；§7 增一个把选定语义钉死的断言（`x/../y` → ENOTDIR/fail-closed），使该分歧有回归锚。注意：本 finding 不建议改用 ALLOW_MISSING；另一个可选减负方向（非缺失链 fast path）见 Finding 1。
- **修复风险（低）**: 低（一段文档 + 一个断言）。
- **严重程度**: 低。

## Conclusion

**pass-with-risks。**

- 计划与 goal 的绑定契约（含用户已授权的“保留 missing target + deny 最近 existing ancestor”保守候选方向）逐项可映射，未发现 goal drift、未授权依赖升级、compat 框架或 future-slice 预埋；verify 两轮契约未发现可伪接受不存在目标的组合；证据链（baseline ambiguity → materialization → ancestor 实测 → 现状 `--verify` 失败）完整且被独立复核。
- 放行风险集中在两点，均为**非阻断的契约补强**：Finding 1（中）要求把解析器相对现状/内核的三处行为转变显式披露并配测试/报告；Finding 2（低）要求补齐“不用 ALLOW_MISSING”的论证并钉死语义。二者可由 controller 作为 accepted plan 修订吸收（或并入 S1 的实现约束与测试清单），无需方案重写或重新 goal confirmation。
- Open Question 2（A/B/C 的语义裁定）与 Open Question 1（ancestor 级联）应由总控在裁决 step 中关闭，再交 gpt-6-sol 实施。
