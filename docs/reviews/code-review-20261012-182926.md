## Abstract case outcomes (judged from the instruction text, not severity labels)

**(a) Stored JSON list and ordered identity explicit, writer conversion already fixed;
reviewer wants repeated local tuple/list expression spelling.**
Non-blocking. This is "明确约束已覆盖的局部表达式" / "措辞重复" under Gateflow L232–234
and Planreview L124–127: the contract and identity/order are decided, only the local
spelling is disputed, and local expression belongs to the implementation scope
(L162–163: "实现者在 approved scope 内决定局部实现"). Handling: controller adjudicates
per the existing states (e.g. `rejected-with-reason`, or `deferred-with-owner` with
destination/rationale if kept as a note) with destination = implementation/code review
and a stated non-blocking basis; the reviewer must not loop it as a plan blocker. It
does not touch the review pass conditions, because no `accepted` finding is created.

**(b) Public identity/order or allowed state transition genuinely undecided.**
Blocking — must not be softened by (a)'s analogy. Decided-identity semantics and
state transitions sit in the "must not be re-decided" list (Gateflow L161–162), are
required plan/slice contents (L177, L206), and are named as still-blocking real
contract/state blockers with no rename/defer/waive (L234). Independently, an undecided
public order or transition is a "blocking open question affect[ing] … contract …
state transition … user-visible behavior" (stop conditions L130–131, L153–155) and
fails the review pass condition "没有 blocking open question" (L248). Planreview's
Attack Surface (scope/ownership/state-machine clarity) reaches the same result.

**(c) Local code bug established only after implementation against a clear contract.**
Non-blocking at plan; destination = implementation/code review. Gateflow L232–234:
issues "只能通过已实现代码判断…不得反复阻塞 plan", routed to "implementation /
code review 等 destination"; L163: "实际代码问题由 code review 检查"; Planreview
L124–127 mirrors this. Raising it during plan review would contradict the explicit
routing rule; the correct handling is a code-review finding once implemented.

**(d) Fix changes one ownership boundary; prior evidence holds for unchanged parts; a
new evidenced counterexample affects another boundary.**
Handling under Gateflow L236–238 / Planreview L93–94: reuse the prior evidence for
the unchanged parts (still valid and unaffected conjunctively); re-verify the old
evidence for the changed boundary (artifact change = new version, affected evidence
must be re-verified); expand re-review scope to the boundary hit by the new evidenced
counterexample (enumerated expansion trigger); do **not** redesign/rescan unaffected
parts; still satisfy the applicable independent review, gate order, and approval
requirements (L238). The new counterexample is a legitimate current-goal signal and
cannot be dismissed under (a)'s wording-repetition analogy.
