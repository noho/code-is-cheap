## Findings

### 1-未修复-中-更新前生成的既有 archive 会被 restore 整体拒绝，且无代际区分与补救说明

- **入口/函数**: `restore` → `restore_environment()` 的 required 成员校验循环（USB 维护副本）
- **文件(行号)**: `scripts/backup/agents-backup-restore.sh:406`（`required_paths` 新增 collector）、`:443-448`（硬失败循环）；对照旧版 `agents-backup-restore.original.sh:78-87`（旧 `backup_paths` 不含 `.local/bin/agent-run-result.py`，manifest 也未变：仍 `format_version=1`）
- **输入场景**: 用更新前的脚本（即当前 USB 在线副本，baseline hash `237c12a8…`）生成的任何 payload，执行 `bash agents-backup-restore.sh restore [--yes] [--install-deps]`
- **实际分支**: `tar -tf "$ARCHIVE_PATH" '.local/bin/agent-run-result.py'` 返回非零 → 打印 `Required path is missing from archive: .local/bin/agent-run-result.py` → `exit 1`（发生在确认提示与 `~/.agent-restore-backups` rollback 之前）
- **预期行为**: archive 是该工具的主要输入；更新后应要么继续恢复既有 payload，要么至少能区分 archive 代际并在失败时给出可执行的补救路径（例如在 target 运行 `sync-agent-tools.sh` 获得 collector）
- **实际行为**: 所有存量 archive（按构造必然缺 collector 成员，包括换机场景下 USB 上携带的那份唯一 payload）被整体拒绝；仅输出一行成员名，无补救指引；README/implementation.md 均未记录此输入契约变化；新式 archive 未写新型代际标记，restore 无法区分新旧
- **直接证据**: 新增 required 项（:406）与循环条件（:444）；旧脚本备份清单（original:78-87）不含该成员 → 旧 archive 必然缺该 member；已交付测试 `test_missing_collector_rejects_backup_and_archive_before_target_changes`（`tests/test_agent_backup_restore.py:210-223`）以「删成员的 archive」断言 restore exit 1、target 未改动——证明这是当前实际行为（本次独立运行通过）；`validateRuntime`/runner 侧（`agent-sandbox-launch.mjs:137`、`claude-agent-run:388` 的 `die`）仅证明 collector 对**新环境**是运行时必需，不要求拒绝旧 archive
- **影响**: 主用例（磁盘故障后从既有 payload 恢复 / 换机迁移）被阻断；无数据损坏与静默失效（失败在 rollback 前，行为响亮），但若源机已不可用则只能手工解包 tar，工具本身无路可走；`verify` 仍可用
- **建议改法和验证点**: 为 archive 引入显式代际（例如新备份写 `format_version=2`），restore 对 v1 archive 将 collector 降级为「警告 + 提示在 target 运行 `sync-agent-tools.sh` 补装」，对 v2 archive 保持必需 + 常规文件/符号链接/目录校验；若维持一律硬失败，则至少补充明确补救文案并在 README 记录该输入契约变化。验证点：合成 v1 archive（缺成员 + `format_version=1`）可完成恢复且打印补装指引；v2 archive 缺成员/符号链接/目录仍在 rollback 前 exit 1
