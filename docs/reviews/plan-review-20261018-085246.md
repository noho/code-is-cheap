## Challenged areas upheld (no finding)

These dispatch-focus areas were adversarially examined and found **necessary and goal-consistent**, not unsupported architecture:

1. **Launcher plumbing (runner↔launcher/helper launch-outcome channel)** — Necessary. Goal requires "failures before the CLI starts remain runner setup failures" *and* faithful native exits. Code facts show these are currently indistinguishable; sentinel exit codes collide with genuine native 1/2/126/127 (matrix row 128 vs 127 is a real distinction: shell `command not found` 127 must not be reported as native 127); stderr parsing and "missing events" inference are explicitly and rightly barred (detail mode has no event stream). The plan confines the mechanism: invocation-local, internal, not a public CLI feature, no persistence, closed before agent tools inherit it, interactive use preserved, mechanics left to the implementer with required distinction tests. This is the minimum mechanism that satisfies the goal; removing it would silently retain the misattribution the goal orders removed.
2. **Wrapper failure precedence (N/W matrix)** — Necessary and correct. "Native nonzero takes precedence" satisfies "native nonzero remains exact"; `W` (0/1) + diagnostics + stderr make wrapper I/O/collection failures visible "without misattributing them to the native process", which the goal explicitly demands the plan spell out. Collector crash with no report (row 125) proves outer must be able to signal delivery failure without inventing a report; extending the same precedence to all W=1 cases is the coherent choice. Ownership split for Codex `--last-message` is well-drawn: native non-production of the optional file is a native observation (`W=0`); failure of the wrapper's own copy after its temp file exists is wrapper-owned (`W=1`), with no-clobber and retained-temp preserved. Compression of underlying wrapper codes into `W∈{0,1}` with causes retained in diagnostics is deliberate and documented; the additive `wrapper_exit_code` field is the minimum needed to represent N≠0 ∧ W=1 simultaneously (row 124), not schema redesign.
3. **Status changes** — Each maps to a confirmed goal bullet and to verified current behavior (assumptions 1–2): `rejected` removal (it is the acceptance classifier the goal bans), `failed` narrowed to observed native nonzero (a zero-exit process must not be labeled failed), additive `incomplete` (goal requires incomplete/missing-final visibility without fabricating success), `terminal` stops manufacturing Claude `failed` from a `success` subtype (honest metadata), collector successful-report exit always 0 (goal evidence lists the promotion as a bug), `runner_exit_code` never synthesized from `validation_status`. `result_status=not_assessed` is already unconditional in code; codifying it is not drift. Structural (not semantic) ownership rules plus the explicit keyword-list ban keep parser and business acceptance cleanly separated: `agent_status` describes the interaction's structure, `result_status` stays unassessed, and prose ("blocked", "unable", "skeleton", "import failed") cannot move any field — matching the user's interaction contract (runtime 0 + explanatory final = successful interaction even without a report artifact).

Scope is minimal and single-slice with justified file boundaries (runners/collector, narrow launch boundary, wording-only preflight, migrated tests, four consumer docs; agent-sandbox touched only on proven dependency). No supervisor/persistence/retry/provider work — the unauthorized historical proposals are explicitly excluded. Sequencing (one slice shipping code+regressions+docs together) is right for a public contract change. The behavior matrix covers every goal success signal (import-failure-final + missing report → 0; skeleton without semantic verdict; check/SSE/tool diagnostics at 0; exact native nonzero; empty/absent/damaged final honestly exposed) for both runtimes plus postprocessing and prelaunch paths, and the required cross-combination tests guard against re-coupling the axes.

## Findings

### 01-未修复-中-runner 侧 launch-outcome channel 缺失或不可读时的归属语义未定义
- **位置**: plan.md "Process and failure ownership" → "Native versus setup and delivery" item 4（"Preserve ordinary interactive launcher use when the runner-specific channel is absent"）；One implementation slice（`agent-tools.zsh` / `agent-endpoint.py` 边界）；Residual risks 表 "Installed skill/launcher/runner skew" 行
- **问题类型**: 契约缺失 / open question 未收敛
- **当前写法**: item 4 只规定了 **interactive** 场景下 channel 缺失时保留 launcher 原有行为，以及 channel 的机制约束；没有规定 **runner 调用** launcher/helper 时 channel 缺失、未写入或半写（自定义 `AGENT_TOOLS_FILE`、同步窗口期的旧版 `agent-tools.zsh`、launcher 在写 channel 前被硬杀）应如何归属 N/outer exit。
- **反例/失败场景**: 实现者面对 channel 无信息 + 状态 1/127 时自行选择：(a) 回退“状态即 native”——在被文档支持的自定义 launcher 路径上原样复活本次要修的误归属（setup 失败被写成 native 1/127）；(b) 一律当 setup 2——把真实 native 1/127 或已执行 CLI 的返回误报为 setup，违反 "A real CLI returning 1, 2, 126 or 127 is still a native return"。仓库内即存在该形态：`tests/test_agent_run_results.py:41–44` 通过 `AGENT_TOOLS_FILE` 安装合成 launcher 函数（无 channel），该 harness 迁移方式在计划的测试节中未点名。
- **为什么有问题**: goal 要求 "Failures before the CLI starts remain runner setup failures" 且 "Do not fabricate … unknown exit codes"；channel 不可得时两种自发明语义各违反其一。runner help 将 `AGENT_TOOLS_FILE` 列为受支持的扩展点，因此这不是纯部署期问题（skew 行只覆盖安装偏差，不覆盖受支持的自定义 launcher）。
- **直接证据**: plan.md item 4 原文仅 "Preserve ordinary interactive launcher use when the runner-specific channel is absent"；`scripts/codex-agent-run:54–56` / `scripts/claude-agent-run:53–55`（`AGENT_TOOLS_FILE` 环境说明）；`tests/test_agent_run_results.py:41–44`（合成 launcher 工具文件）；goal.md "Do not fabricate native success, final answers or unknown exit codes"。
- **影响**: 生成错误代码（静默恢复误归属或误报 setup）；与 goal 的正确性条件冲突；后续 code review 需重新裁决本应在 plan 层确定的契约。
- **建议改法和验证点**: 在 item 4 增加一句 runner 侧规则，二选一并写明理由：channel 缺失/不可读时**不得**推断 native 归属——要么按 setup failure（outer 2，原始原因注明 channel 不可用），要么在报告中以显式 diagnostic 标注 "launch outcome unknown" 且不得声称 native attribution（含 `agent_status=incomplete` 类处理）。同步点名：`test_agent_run_results.py` 合成 launcher 迁移为实现 channel，或显式作为 "channel 无" 用例覆盖所选规则。验证点：fake launcher（无 channel）+ 真实 native 127 的区分测试列入 item 4 的 distinction tests。
- **修复风险（低/中/高）**: 低（一句契约 + 一个测试用例）
- **严重程度（低/中/高/严重）**: 中（受支持扩展点上会复活本单修复的误归属；但边界窄、可低成本收敛）

### 02-未修复-低-opt-in host-disabled 用例的断言迁移方式与“不执行”约束互相矛盾
- **位置**: plan.md "Code evidence and root cause" 末段（"the official host-disabled case must assert the observed native outcome rather than assume absent business output means nonzero"）vs "Offline validation and repository checks" 第 160 段（opt-in suites "retain their directly affected assertions, record them as unexecuted coverage, and do not enable them"）
- **问题类型**: 测试缺口 / 缺少必要实现依据
- **当前写法**: 一边要求该 opt-in 断言改为 "assert the observed native outcome"，一边规定本单不执行 opt-in 套件；离线实现者无法得知真实 mimo host-disabled 的 native outcome，"retain their directly affected assertions" 对需要改动的断言措辞含混（保留原样 vs 迁移后保留覆盖面）。
- **反例/失败场景**: 实现者 (a) 猜测并硬编码某个 native outcome（未经验证的断言），或 (b) 原样保留 `assertNotEqual(returncode, 0)`（`tests/test_official_catalog_runtime.py:458–467`）——若真实形态是 native 0 + 解释性 final + 无产物（恰为 goal 首条成功信号的 live 版），该断言固化的是本次要移除的拒收策略，套件日后启用即误导或假红。
- **为什么有问题**: 计划正确识别了该断言的旧策略依赖，却未给出在"不执行"约束下可确定的迁移形态；与计划自己的验证原则 "Do not globally replace every old 1 with 0 without checking the owner" 不对称。
- **直接证据**: plan.md 两处原文如上；`tests/test_official_catalog_runtime.py:368`（`OFFICIAL_CATALOG_RUNTIME_TESTS` 门控）、458–467（`test_mimo_explicit_host_false_fails_visibly` 断言 `returncode != 0`、`validation_status != 'passed'`、无 `result.txt`）。
- **影响**: review 不可验收（未执行套件中的断言改动无证据）；或遗留旧拒收语义断言造成后续返工。
- **建议改法和验证点**: 明确迁移为**结果无关**断言：outer exit 与 `runtime_exit_code`（W=0 时一致）及报告字段自洽、无人为业务判定，而不是断言具体数值；并按"unexecuted coverage"记录。验证点：该用例的断言文本可在离线 code review 中判定，不需要跑 native 套件。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低
