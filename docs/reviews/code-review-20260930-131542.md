### 01-未修复-高-PR diff 仍未与记录的 head/base OID 绑定到同一不可变版本

- **入口/函数**: Deepreview PR Review Mode 的 PR facts、diff snapshot 和深挖代码版本选择。

- **实际分支**: 当前命令只保存 `gh pr diff` 的任意当前输出并哈希，再做前后 OID 查询。`gh pr diff --help` 只接受 PR number/url/branch 和过滤 flags，没有 commit/OID pin。命令没有从已记录 OID 构造 diff，也没有证明该 snapshot 的两端就是记录的 OID。
- **预期行为**: PR diff 必须由精确的 `base_oid...head_oid` 生成或由明确绑定这两个 OID 的 API 响应产生；深挖代码也必须来自同一 head OID。前后 OID 只能检测明显移动，不能单独证明中间 diff 的来源。
- **实际行为**: 技能文本声称绑定版本，但推荐执行路径仍是可变 PR 引用。若 diff 来自另一版本而 metadata 查询恰好未捕捉移动，artifact 会把混合输入写成同一版本审查。
- **直接证据**: `gh pr diff <pr_number> > <review-diff-snapshot>` 后只做 `shasum` 和再次 `gh pr view`；没有 exact-OID compare/fetch/diff。`gh pr diff --help` 的 usage 是 `gh pr diff [<number> | <url> | <branch>]`，没有 head/base commit 参数。
- **影响**: 高成本 review 结论可能基于错误 diff、错误 implementation/tests 调用链或错误 base，且 artifact 看起来身份完整；这是静默审查正确性问题。
- **建议改法和验证点**: 用 GitHub compare API 的精确 `baseRefOid...headRefOid` 生成并保存 diff，或只读 fetch 两个精确 OID 后执行 `git diff <base_oid>...<head_oid>`；记录响应/对象身份与 hash，再从同一 head OID 读深挖文件。对 fork/对象不可达时明确 blocker。验证 head/base 中任一移动、base-only 移动、本地 checkout 不等于 head 三个场景。
