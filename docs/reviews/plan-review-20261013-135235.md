## Open questions (non-blocking; controller adjudication or implementation clarification)

1. **OQ-1 — Unknown pre-turn frames on Codex.** The plan enumerates allowed pre-turn frames (top-level `error`, completed error items) and lists "work before turn" as rejecting, but does not explicitly state the disposition of unknown non-diagnostic frames between `thread.started` and `turn.started` (e.g. `rate_limit_event` or future telemetry). Native 0.162.1 never emits such frames, so this cannot affect S1–S6; recommend the implementation follow the plan's fail-closed posture (reject) or state "existing non-proof handling retained" explicitly in the implementation artifact. Owner: implementation agent → code review.
2. **OQ-2 — Null-vs-absent rule restatement.** The Claude metadata table implements SDK nullability exactly (nullable `stop_reason`/`api_error_status` tolerate null; plain-optional `terminal_reason`/`deferred_tool_use`/assistant `error` treat explicit null as malformed). This is correct per evidence but the general rule is implicit; restating it in the implementation artifact would prevent an implementer from " symmetrically" tolerating null on the optional fields and silently weakening the fence. Owner: implementation agent.
3. **OQ-3 — `agent_status` under parse damage.** The plan says `agent_status=completed` requires "valid same-execution successful terminal/final proof" but also that parse damage leaves "native completion evidence/final text … displayable." Existing tests assert `agent_status=completed` with `validation_status=rejected` for corrupt-line-with-valid-terminal cases (lines 733–749). Recommend pinning the current behavior (terminal proof seen + exits zero → completed; rejection carried by `validation_status`/exit) so unchanged assertions stay unchanged. Either reading keeps the outer exit nonzero, so this is not safety-critical. Owner: implementation agent → controller adjudication if ambiguous during implementation.
