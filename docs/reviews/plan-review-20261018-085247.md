## 3. Assessment of the challenged launcher plumbing

**Verdict: necessary, not unsupported architecture.**

The goal imposes two requirements that cannot both be met by inspecting launcher exit status alone:

- a real CLI can return 1, 2, 126, or 127;
- a launcher/helper can fail before exec with the same conventional codes.

Missing native events cannot distinguish the two because a real CLI may start and produce no usable events, and the goal explicitly forbids inferring "not started" from absent output. Duplicating provider setup in the runners would create two sources of truth for credentials/models/shims and is forbidden by the plan. A private, invocation-local signal between runner and launcher/helper is therefore the minimal mechanism that satisfies the goal.

The plan's constraints on that channel are appropriate and avoid overreach:

- explicit internal control channel, not parsing model output or human stderr;
- no reserved native exit number as a setup sentinel;
- no inference of native zero from absent metadata;
- ordinary interactive launcher use must still work without the channel;
- the channel must not be inherited by the CLI/tools and is not persistent storage or a public feature;
- the exact local mechanism is left to the implementer, but the distinction tests are mandatory.

That is the right division between plan-level contract and implementation detail. The required tests (setup errors never enter native; genuine native nonzero exact; native 126/127 distinguished from exec failure; prompt-pipe behavior cannot replace native status) are exactly the tests that would expose an unreliable mechanism.

One open question remains: the plan does not prescribe whether the channel is a close-on-exec pipe, a private marker, or another mechanism. That is acceptable at plan level, but the implementation should prove non-inheritance and exec-failure detection, not just happy-path signaling.

## 4. Assessment of wrapper failure precedence

**Verdict: consistent with the goal; no simpler alternative found that preserves both native fidelity and wrapper visibility.**

The plan's N/W matrix is:

```text
before CLI launch: setup/usage failure -> 2, no fabricated native report
after CLI exit:    N != 0 -> N
                   N == 0 and W != 0 -> 1, explicitly a wrapper delivery failure
                   N == 0 and W == 0 -> 0, regardless of diagnostics or task acceptance
```

This satisfies the goal's two independent obligations:

- native nonzero is returned exactly and is never replaced by collector/check status;
- wrapper delivery failure is visible without being described as a native failure.

The alternative of always returning 1 on wrapper failure would hide the exact native code. The alternative of always returning 0 on native success would hide the wrapper failure from the outer exit. The plan's precedence plus the additive `wrapper_exit_code` field, stderr diagnostics, and doc migration is the most faithful single-exit encoding.

The plan correctly prevents protocol/artifact/canary findings from setting W: checks cannot rewrite the native exit. The wrapper-owned cases are limited to last-message copy/destination failure, collector invocation/completion failure, and serialized-report delivery failure. Missing/malformed/mismatching/unreadable native outputs remain diagnostic observations when a completed collector can report them. That boundary is coherent: the collector's success is about producing a report, not about the native data being complete or clean.

Residual risk (nonblocking): a caller that reads only the outer exit cannot distinguish `N=1, W=0` from `N=1, W=1`; when the collector itself fails, there is no report at all. The plan requires stderr to carry the native status, wrapper cause, and log paths, and the docs must direct callers to `agent_status`, `wrapper_exit_code`, and stderr. This is a caller-integration risk, not a plan defect.

## 5. Assessment of the status changes

**Verdict: the status changes are necessary and directly traceable to the goal; they are not an unrelated schema redesign.**

- `agent_status=incomplete` is necessary because the current `failed` conflates "the native process failed" with "collection cannot establish complete final ownership." The goal explicitly requires honest incomplete/partial/missing-final visibility and says native 0 plus a final is a successful interaction even when the work is incomplete. Keeping `failed` for both would reproduce the misattribution the work unit exists to correct.
- Removing `validation_status=rejected` is necessary because it is an acceptance label. Turning it into a diagnostic rollup (`passed`/`needs_review`) lets the caller inspect `errors`, `anomalies`, `artifacts`, and `canary_status` without the wrapper declaring a business verdict.
- Retaining Claude's reported `subtype` instead of manufacturing `terminal=failed` is necessary to avoid a synthetic native negative signal. The current code does manufacture `failed` for `is_error=true`, refusal, `max_tokens`, and other non-success metadata; the plan's target is the observed subtype plus diagnostics.
- `wrapper_exit_code` is the one additive field. It is minimal and necessary to represent a native nonzero and a wrapper failure simultaneously; `runner_exit_code` alone cannot carry both under native precedence.
- `agent_status=completed` for native 0 + attributable final, including a final that reports inability, missing input, an environment obstacle, or incomplete work, matches the user's clarified interaction contract.
- The plan explicitly forbids keyword lists, semantic answer classifiers, final-content task checks, and path extraction from prose. Canary proof parsing and tool-syntax diagnostics remain informational. This is the correct parser/business distinction.

Compatibility note: the plan keeps `schema_version=1` while adding a field and changing enum values (`incomplete` added; `rejected` removed; `terminal` semantics changed). The plan calls this an explicitly documented behavioral migration, and the goal assigns external caller migration to later work. That is acceptable, but the docs should state that `schema_version=1` is not a guarantee that the status enum is unchanged; otherwise a caller that gates on `schema_version` can still be surprised.

## 6. Matrix and parser/business distinction assessment

The required behavior matrix covers the important families:

- native 0 + final + no checks → 0/completed/passed;
- native 0 + final explaining an import failure/environment obstacle/inability + missing optional report → 0/completed/needs_review;
- mechanically valid skeleton artifact → 0/completed/passed absent other diagnostics;
- canary and artifact failures → 0/completed/needs_review;
- ordinary tool failures, recovered SSE/retry diagnostics, malformed non-proof frames → 0/completed/needs_review;
- valid negative completion/limit/refusal/error terminal with final and native 0 → 0/completed/needs_review;
- missing/invalid/conflicting proof, missing/empty/invalid final, damaged output → 0/incomplete/needs_review;
- unreadable stderr with final proof → 0/completed/needs_review;
- native nonzero → exact N/failed/needs_review;
- Codex last-message missing/mismatching → 0/completed or incomplete/needs_review; copy/destination failure → 1, W=1;
- collector process failure → 1 after native 0, or exact N after native nonzero, with no trustworthy report;
- setup failure → 2 with no native report;
- native 126/127 exact; early-exit CLI/prompt pipe does not replace native status;
- unknown native status → observed runner signal status or wrapper failure 1, no invented report.

The distinctions are structurally correct: terminal presence/validity, final ownership, identity, and execution order are visibility proofs; they do not decide task success. Native negative metadata is reported, not converted into a synthetic process failure. Missing final/ownership makes `incomplete`, not `failed`. Checks never set W. The matrix does not classify prose.

I found two matrix details worth tightening during implementation; neither is a blocker:

1. **Copy failure with no attributable final.** The copy-failure row says `completed / needs_review` "if event final proof exists" but does not state the else. The field table implies `incomplete / needs_review`. An explicit cell and a test would remove ambiguity.
2. **Structured Claude negative fields beyond the named examples.** The plan names `is_error`, non-success subtype, `stop_reason=refusal/max_tokens`, and structured limit/error. The current collector also rejects `deferred_tool_use`, non-`completed` `terminal_reason`, non-null `api_error_status`, and non-empty `errors`. The plan's "valid negative terminal metadata ... reported, but native 0 still represents a completed interaction" should be read to cover these; the implementation should record them as diagnostics and keep `completed` if a final is attributable. The plan should state this explicitly or add a fixture.

A related edge case: when the latest completed Codex `agent_message` is empty but an earlier completed message is readable, the plan's "latest-completed-message checks" and "preserve readable partial/candidate text" should be reconciled explicitly. The safest implementation keeps the earlier readable text as the candidate while marking `final_valid=false`/`incomplete`. This is an implementation detail with a clear test, not a plan blocker.

## 7. Compatibility and regression-test assessment

The existing tests are not merely old assertions; they are the old acceptance oracle. `assert_completion` at `tests/test_agent_run_results.py:106-114` derives the expected process exit from `validation_status`, and multiple tests assert `rejected`/1 for missing artifacts, canary mismatches, invalid finals, and postprocessing errors. The plan correctly requires decoupling the helper from `validation_status` and migrating assertions by owner rather than mechanically replacing 1 with 0. The baseline pass (57 tests) confirms this is a real migration surface.

The planned regression coverage is strong and matches the goal's success signals:

- direct import-failure-final + missing-report fixture for both runtimes;
- mechanically valid skeleton fixture with no business-content inspection;
- all-clear vs blocked/unable prose with identical protocol treatment;
- malformed/truncated streams, duplicate/conflicting terminals, invalid identity, native negative metadata, late token disappearance, hard-linked artifacts;
- ordinary and recovered diagnostics combined with missing artifacts/canary and real postprocessing/native failures;
- actual launch functions/helpers against fake CLIs with native-entry markers, setup failures, exact native nonzero, 126/127 vs exec failure, and prompt-pipe behavior;
- missing last-message (`W=0`) vs copy failure (`W=1`) at native 0 and 7, with no-clobber and retained temp paths;
- collector-process failure injection at native 0 and 7, including summary-output failure, checking caller stderr rather than requiring a report;
- `--detail` raw-stream/redirection behavior and session/launch arguments;
- preflight command generation, envelope setup, and the staged-install test with temporary `AGENT_RUN_BIN_DIR`/`AGENT_TOOLS_TARGET`.

Gaps/risks to track during implementation:

- add the copy-failure + missing-final case explicitly;
- add a non-inheritance/direct-launcher-use check for the internal channel;
- document the `schema_version=1` vs enum-change compatibility boundary;
- confirm the `deferred_tool_use`/structured-negative handling with a fixture;
- the install suite's local-bind test cannot run in this sandbox; that is an environment limitation, not a plan defect. The plan's validation command should be run in a normal environment.

The plan's full validation commands are appropriate: focused suites, shell syntax checks, skill validation, full unittest discovery with native/kernel opt-ins disabled, and `git diff --check`. It correctly refuses to claim live/provider coverage and records opt-in suites as uncovered.

## 8. Open questions

1. **Exact launch-outcome channel mechanism.** The plan leaves the mechanism to the implementer. The required tests define the acceptance, but the implementation should explicitly prove that a pre-exec failure and a genuine native 126/127 are distinguishable, and that the channel is not inherited by the CLI. Owner: `gpt-6-sol` implementer / controller; destination: implementation evidence and final code review. Classification: fixed in current slice (required tests).
2. **`schema_version=1` with changed status enums.** Should the version be bumped, or should the docs explicitly state that version 1 is structural only and that callers must tolerate `incomplete` and the absence of `rejected`? Owner: user/caller maintainers; destination: caller integration after merge. Classification: assigned to later work unit (documented migration).
3. **Copy failure with no final proof.** Confirm the intended report status is `incomplete / needs_review` with `wrapper_exit_code=1`, and add a fixture. Owner: implementer; destination: implementation tests. Classification: fixed in current slice.
4. **Claude `deferred_tool_use` and other structured negative fields.** Confirm they are diagnostic-only when a final is attributable, rather than an invented `failed`/`rejected`. Owner: implementer; destination: implementation tests/code review. Classification: fixed in current slice.
5. **Codex empty latest `agent_message`.** Confirm whether an earlier readable completed message is retained as the candidate when the latest completed message is empty/non-string. Owner: implementer; destination: implementation tests. Classification: fixed in current slice.
6. **Unreadable retained output and `W`.** The plan deliberately treats collector-observed unreadable/corrupt native output as a diagnostic (`W=0`, `incomplete`), not a wrapper delivery failure. Confirm the docs tell callers to inspect `errors`/`agent_status` rather than relying only on `wrapper_exit_code`. Owner: caller maintainers; destination: README/skill migration and caller integration. Classification: assigned to later work unit.
