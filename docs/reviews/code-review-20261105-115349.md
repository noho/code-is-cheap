## Findings

### 1-未修复-中-sync reports success without confirming that the restarted shim serves route 8796

- **入口/函数**: `scripts/sync-codex-agent.sh` loaded-service restart path; `codex-auto-review-shim` multi-route bind loop in `main()`.
- **文件(行号)**: `scripts/sync-codex-agent.sh:168`, `scripts/sync-codex-agent.sh:169`, `scripts/sync-codex-agent.sh:173`, `codex-agent/shim-routes.json:78`, `codex-agent/bin/codex-auto-review-shim:533`, `codex-agent/bin/codex-auto-review-shim:537`, `codex-agent/bin/codex-auto-review-shim:539`.
- **输入场景**: An existing shim service is loaded and `sync-codex-agent.sh` deploys the new Hy route while another process already listens on 8796, or the restarted service otherwise exits before binding every configured route.
- **实际分支**: `launchctl print` finds the loaded service, so the script executes `launchctl kickstart -k`. A successful restart request is treated as deployment success without waiting for the process or checking the route listeners. On startup, the shim binds routes in declaration order, reaches 8796, gets `OSError`, prints `cannot bind`, and returns exit 1.
- **预期行为**: Sync must report success only after a bounded post-restart check proves the loaded job is stable and every route port from `shim-routes.json`, including 8796, is listening. A failed startup or port conflict must produce a nonzero sync result and identify the missing port/service log.
- **实际行为**: The script can print `restarted launchd service` and `Synced codex-agent cards` even though the new shim immediately exited and no route is served. Because one failed bind aborts the multi-route process, the launchd `KeepAlive` setting can then repeat the same crash cycle and temporarily take down the already-existing cloud Codex routes as well.
- **直接证据**: The sync restart branch at lines 168-176 only checks the exit status of `kickstart`; it has no readiness poll. The shim’s bind loop at lines 533-539 returns 1 on the first failed bind. The service plist uses `KeepAlive=True`, while the stricter readiness helpers already present in `codex-auto-review-shim-service:111` and `:202` are not used here. `tests/test_model_catalog_generation.py:391-410` covers only a nonzero `kickstart` result and a nominal zero result, not “kickstart accepted, process exited, port absent.”
- **影响**: A routine resync can falsely certify a broken deployment and leave all shim-backed Codex profiles unavailable until the operator discovers the port conflict or service crash loop manually. This is a startup-success correctness gap, not a request to guarantee ongoing vendor availability.
- **建议改法和验证点**: After `kickstart`, poll the loaded job and all route ports for a short bounded interval; fail with the service log/conflict details if any port never listens. Reuse one dynamic `shim-routes.json` port parser rather than hard-coding 8796. Add a focused test where `launchctl` reports the job loaded and accepts `kickstart` but 8796 never listens; assert sync exits nonzero and does not print its final success line. Add a real loopback conflict case to prove the shim’s single-bind failure behavior.
- **修复风险（低/中）**: Medium-low. Readiness polling must use a bounded retry window and account for launchd state transitions, but no product protocol or catalog contract needs to change.
- **严重程度（中）**: Medium.
