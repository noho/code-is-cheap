- **入口/函数**: `scripts/repair-codex-reasoning-history.py` 的 `--drop-reasoning-model` 手工恢复路径；用户入口是双语 README 的跨 provider resume 恢复示例。
- **文件(行号)**: `README.md:553-554`、`README.zh.md:507-508`、`codex-agent/profiles/kimi/config.toml:5`、`scripts/repair-codex-reasoning-history.py:40-53`、`tests/test_official_catalog_runtime.py:435-437`、`tests/test_official_catalog_runtime.py:449-451`
- **输入场景**: 新建 Kimi 会话使用本 PR 的逻辑模型 `k3`，rollout 的 `turn_context.payload.model` 因而是 `k3`。该会话切到官方 OpenAI endpoint resume 后仍出现 `invalid_encrypted_content` 或缺失 reasoning item ID，用户按 README 执行手工 drop 示例。
- **实际分支**: `repair_lines` 读取 `turn_context` 的 `current_model="k3"`；`current_model in drop_reasoning_models` 对文档传入的 `{"kimi-k3"}` 为 false，reasoning item 被原样保留。CLI 返回 0，并警告没有 item 命中。
- **预期行为**: 当前逻辑会话和历史 wire-name 会话都应能由文档示例清除第三方 reasoning；至少当前 README 示例应明确传入 `k3`，或同时接受 `k3` 与 legacy `kimi-k3`。
- **实际行为**: 小型 dry run 中，`--drop-reasoning-model kimi-k3` 输出 `affected reasoning items: 0` / `dropped reasoning items for kimi-k3: 0`；改用 `k3` 才输出 `affected reasoning items: 1`。无 `--apply` 时文件保持两行不变。
- **直接证据**: PR 将 `codex-agent/profiles/kimi/config.toml` 的模型从 `kimi-k3` 改为 `k3`，shim 逻辑路由也改为 `k3`；Qwen 同类持久化测试证明 `turn_context` 记录的是逻辑卡模型。`repair_lines` 只做精确集合匹配，且 unmatched 时仍返回成功。实测路径 `/tmp/pr55-k3-reasoning.IqQhdc` 保留。
- **影响**: 对当前 Kimi 会话，文档指定的手工恢复命令不能删除目标 reasoning，跨 provider resume 的已知失败可能继续存在；混合 rollout 还可能只修掉 MiMo 部分而留下 Kimi 部分。warning 可被忽略，用户可能误以为恢复已执行。
- **建议改法和验证点**: 在双语示例中加入 `--drop-reasoning-model k3`，可保留 `kimi-k3` 以覆盖历史 rollout；新增当前逻辑模型 `k3` 与 legacy `kimi-k3` 两组回归。验证 dry-run/apply 的命中数、备份内容和混合模型部分修复行为。
