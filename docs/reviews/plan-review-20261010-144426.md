## Findings

### 1-未修复-[高]-S1 bundles three independently testable behavior changes into one oversized implementation slice
- **位置**: `plan.md` lines 25-34 (`Slice S1: ordinary calls with opt-in checks`), especially allowed source/docs and tests; implementation decisions 1-11
- **问题类型**: 切片过粗 / 过度耦合 / 不可直接实施
- **当前写法**: S1 is presented as “one integrated behavior slice” spanning `sub-agent-preflight`, both runners, `agent-run-result.py`, a rewritten `sub-agents` skill plus a new advanced reference, both READMEs, and two test modules. It simultaneously changes optional preflight/canary/artifact behavior, runner prompt/setup behavior, and the collected-report schema/timing contract.
- **反例/失败场景**: A regression in terminal usage extraction or wall-clock handling requires re-reviewing and potentially reverting the unrelated ordinary-call/preflight simplification. Conversely, a preflight command bug can block delivery of already implementable report statistics. Because the report schema and command construction are reviewed together with the ceremony removal, a finding in one surface forces one large re-review and weakens failure attribution and rollback boundaries.
- **为什么有问题**: Gateflow requires an implementation slice to be small enough for one implementation pass and one review pass and to represent one verifiable behavior increment (`skills/gateflow/SKILL.md` lines 188-205). The three parts have distinct contracts and failure modes: generated dispatch commands, runner input/setup validation, and parsed runtime metrics. Their documentation coupling does not make their implementation risk inseparable. The goal can remain one work unit while using two implementation slices.
- **直接证据**: `plan.md` line 29 lists eight source/docs targets and line 30 lists two substantial test modules. Decision 10 alone changes runner timing, adapter arguments, JSON fields, null/zero semantics, and terminal-event extraction. Decisions 2-7 independently redesign preflight and its isolation command. Current files are also large enough that one review would cover roughly 1,700 source/doc lines plus focused tests (`sub-agent-preflight` 393 lines, both runners 981 lines, result adapter 358 lines, current skill 357 lines). Gateflow explicitly requires plan review to challenge whether gate cost exceeds implementation risk.
- **影响**: implementation agent must make a broad cross-layer change before any behavior is independently accepted; review regressions can be misattributed; fixes and re-review become expensive; a partial failure has no clean accepted checkpoint.
- **建议改法和验证点**:
  - Split S1 into an ordinary-call/preflight slice (decisions 1-9 and 11) and a collected-statistics slice (decision 10), with disjoint allowed source/test sets and separate completion signals.
  - Keep both slices in the same confirmed work unit and sequence them so no migration or compatibility work is introduced.
  - Validate each slice independently with its own focused tests and review pass; aggregate only after both are accepted.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-[高]-Whitespace-only task sources can still become a dispatchable prompt after heading checks are removed
- **位置**: `plan.md` decisions 2 and 4; focused validation line 38
- **问题类型**: 契约缺失 / 状态机漏洞 / 测试缺口
- **当前写法**: The plan requires exactly one task source and says direct runners must reject whitespace-only tasks, but preflight only retains its existing `-n` / `-s` nonempty-file checks. It removes the fixed-heading checks, then appends a generic final-answer instruction and emits a runnable command.
- **反例/失败场景**: `--task "   "`, a whitespace-only `--task-file`, or a whitespace-only `--prompt-file` passes `-n` or `-s`. After the heading requirement is removed, preflight copies that body, appends the generic instruction, and emits a command. The runner then sees a nonempty `prompt_file`, launches the model, and executes a task with no task context.
- **为什么有问题**: The binding goal requires “sufficient task context” and setup failures before model launch. Removing headings is correct for natural-language tasks, but it also removes the accidental check that previously caught these cases. Direct-runner whitespace validation does not protect the optional preflight path because preflight manufactures a nonempty final prompt before the runner sees it.
- **直接证据**: Current `scripts/sub-agent-preflight` accepts `--task` via `[[ -n "$task_text" ]]` and accepts regular files via `-f/-r/-s`, all of which allow whitespace-only content (lines 226-254). Decision 4 removes heading validation (current lines 304-312) and appends text to the same prompt (lines 288-301). Plan validation line 38 lists plain tasks and invalid/missing prompts but does not require whitespace-only rejection for all three preflight sources; line 39 places whitespace rejection only in runner tests.
- **影响**: preflight can authorize an empty or meaningless model launch, violating the fail-before-launch contract and wasting a provider call while appearing to pass setup.
- **建议改法和验证点**:
  - Define one non-whitespace semantic for `--task`, `--task-file`, `--prompt-file`, runner `--prompt`, runner `--prompt-file`, positional prompt, and stdin; reject empty/whitespace-only input before launch while preserving nonblank source bytes when copying.
  - Require preflight failure with `setup_status=fail` and `command=` for whitespace-only input in all three sources.
  - Add tests for whitespace-only text and files across both runners and all three preflight sources, including a regular file containing only spaces/newlines.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-[中]-Statistics fields lack an exact schema and terminal-event failure contract
- **位置**: `plan.md` decision 10 and focused validation line 39
- **问题类型**: 契约缺失 / 测试缺口 / 并发恢复风险
- **当前写法**: Reports will add `wall_clock_seconds`, `usage`, and `runtime_metrics`; usage is copied only from a terminal runtime event; Claude timing/cost/modelUsage stay in `runtime_metrics`; missing data is null/empty and successful zeros remain zero. The validation bullet calls for “token/cache/reasoning/zero counters” but does not define field names, nesting, types, or malformed/duplicate-event behavior.
- **反例/失败场景**: One implementation emits `usage` as the verbatim terminal object while another normalizes token/cache/reasoning counters; callers cannot rely on the contract. A stream can contain repeated usage updates, a failed terminal with partial metrics, an absent terminal, non-object usage, numeric strings, negative/non-finite elapsed input, or nested zero counters. Each case permits a different result without changing the plan’s test list. This can silently overcount streaming usage, turn unavailable data into zero, or reject an otherwise completed run during additive collection.
- **为什么有问题**: The binding goal requires callers to use runtime-reported statistics without parsing logs and forbids normalization/estimation. That makes the JSON shape and source-selection semantics a real public result contract. An internal adapter argument also needs a name and invalid-input behavior even though the slice says “no new APIs.” Without those decisions, implementation agents must invent them and tests can pass while callers observe incompatible reports.
- **直接证据**: `goal.md` lines 20 and 27 require runtime-reported usage and unavailable metrics to remain unavailable. `plan.md` line 22 specifies sources and a few Claude keys but not output types/nesting or malformed/duplicate behavior. Current `agent-run-result.py` parses terminal events at lines 138-196 but does not expose usage; its return schema is assembled at lines 325-334. Existing synthetic Codex fixtures only include `turn.completed.usage={}` (`tests/test_agent_run_results.py` line 57), so current tests do not establish the proposed statistics contract.
- **影响**: inconsistent compact reports, false cost/token figures, zero-versus-null ambiguity, unnecessary rejected runs from metrics parsing, and caller breakage despite an apparently additive change.
- **建议改法和验证点**:
  - Specify exact output names/types and nesting for `wall_clock_seconds`, `usage`, and `runtime_metrics`, and name the internal adapter argument and its accepted range.
  - State whether `usage` is verbatim terminal payload or a deliberately documented projection; if preserving runtime facts is binding, avoid normalizing or estimating it.
  - Define absent terminal, failed terminal, duplicate terminal, nonterminal/repeated usage, non-object/invalid metrics, nested zero counters, and invalid elapsed input.
  - Assert Codex and Claude terminal extraction separately, including zero-valued cache/reasoning fields, missing metrics as null/empty, failed-run metrics when actually reported, repeated nonterminal usage not being summed, invalid elapsed as null, and unchanged raw `--detail` output.
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

- Should `usage` be the verbatim terminal runtime object or an explicitly fixed projection? The Goal says runtime-reported usage is not normalized, while the plan’s validation wording says “counters”; implementation should not choose silently.
- If S1 is retained as one slice despite finding 1, what explicit user-authorized rationale makes the combined implementation and review cost acceptable? Goal Confirmation line 47 states one behavior slice is sufficient, but Gateflow still requires each slice to be small and reviewable.

## Residual Risks

- Existing callers may have relied on mandatory preflight canary, label, heading, or fixed-report behavior. The Goal explicitly approves this behavior change and excludes compatibility/migration work; track any migration need outside this work unit rather than expanding S1.
- Generic final-answer truth is not mechanically provable. Keep task/project-specific verification with the calling workflow; do not add universal business acceptance.
- Native runtime tool visibility and interrupted-run missing summaries remain existing limitations owned by result-collection follow-up; no new scheduler or mid-run channel is needed here.
- Existing `agent-sandbox` tests provide substantial read/write boundary coverage, and the plan does not propose changing enforcement. The exact generated no-canary/opt-in command should still be exercised through the existing sandbox/native tests when implementation indicates a changed-path risk; this is a validation follow-up, not a request for new hardening.
