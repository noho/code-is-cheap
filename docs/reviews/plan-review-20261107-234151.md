## Findings

### 1-未修复-高-适配范围过宽：按形状展平所有 namespace 缺乏目标必要性与证据，应收窄为已知原生 agent namespace allowlist

- **位置**: 「建议的最小生产方案 → 边界和请求不变量」第 2、3、4 条（“已知 function-only namespace wrapper”“跨 namespace 重名……sanitized400”“未来 namespace metadata……sanitized400”），以及「实现后需要的回归与原生证据」中对应测试范围；对照 controller focus 的范围质疑。
- **问题类型**: 范围漂移 / 目标漂移（goal-bound minimal design）+ 缺少必要实现依据。
- **当前写法**: 适配针对顶层 `tools` 中“已知 function-only namespace wrapper”，以**形状**判定（`type/name/description/tools` + children 全为 function 即展平并入恢复表），未列入的 namespace 名称不做区分；无法无损映射的形状（含未来 namespace metadata）在 flag on 时对整请求 sanitized400。
- **反例/失败场景**:
  1. **可用性**：flag 挂在 Kimi 这条 live route 上、对全部会话生效。宽口径把所有 MCP 子函数名并入平铺命名空间，碰撞面从 5 个固定 agent 名扩展到全部 MCP 工具名（跨 MCP server 重名 `search`/`read` 之类、或与 `exec_command` 等平铺名撞车都现实存在）。一旦碰撞，按计划整请求 400 零发送——用户所有 Codex/Kimi 会话被自己配置的适配器打挂，直到改代码。prototype 只证明了**当前实际请求**名称唯一，不保证后续 MCP 配置。
  2. **未验证前提**：宽方案隐含“恢复出的 `mcp__*` namespace 能被 Codex 正确路由”。`codex-routing-source.json` 只覆盖 `functions` 与 `multi_agent_v1` 的注册/查找，没有任何 MCP 注册键形态证据；prototype 中模型从未调用被展平的 MCP 工具，恢复路径零实测。若注册键不是 `ToolName{ns:"mcp__github", name:...}` 形态，模型的 MCP 调用将变成新的 `unsupported call` 噪声。
  3. **行为外溢**：宽展平让 MCP 工具在模型侧“看起来可调”，改变该 live route 上**所有**会话的模型行为（现状：包裹的 MCP 不产生直接调用——诊断证据；attempt-1 中模型对包裹工具走 `list_mcp_resources` 发现循环）。严格原生测试中父代多余 MCP/发现调用会直接判负（Hy 的三次 `mcp__node_repl.js` 探查先例）。
  4. **无必要性反例**：goal 的 A1/A2/B（spawn、send_input 同 child 继续、wait、子代 `exec_command` 读 fixture）全部落在 `multi_agent_v1` 或平铺函数内；B3 N/A 依据的 descriptor 集合（attempt-1 advertised）只有 `multi_agent_v1`。没有任何当前证据要求展平 MCP 或其他 namespace。
- **为什么有问题**: 与 controller 确认的最小范围（不把完整 MCP 支持变成新目标）、goal-bound minimal design 冲突；计划未给出宽范围的任何 goal 必要性论证，却让其承担真实的 live-route 可用性风险和未验证路由前提。计划第 2 条的“已知”按第 4 条读法是**形状已知**而非**名称已知**，等于把原型的全量展平直接固化成生产契约。
- **直接证据**: 计划边界第 2/3/4 条原文；`routing-verdict.json`（失败原因是 agent namespace 缺失；MCP 展平后零 MCP 调用）；`codex-routing-source.json`（无 MCP 注册证据）；`kimi-tool-namespace-diagnostic.json`（包裹工具 → 无调用、200）；`evidence/kimi/attempt-1/wire.json`（该请求 `tools` 仅 `exec_command` + `multi_agent_v1` wrapper，模型从未需要 MCP 展平即完成平铺调用）；`evidence/kimi/attempt-1/rollouts-sanitized.json`（`list_mcp_resources` 平铺内置调用在 wrapper 存在时照常路由）；controller focus 原文。
- **影响**: 实施 Agent 按文本产出宽适配器 → 碰撞即 route 级 400（goal 验收与用户会话同时被阻断）；MCP 恢复路由不可验收；strict 测试引入父代额外调用风险；后续若要收窄需返工请求/响应两侧映射与整套碰撞测试。
- **建议改法和验证点**:
  1. 将适配集合改为**显式 allowlist：`multi_agent_v1` 与 `collaboration`**（两者均有实测 descriptor/rollout 证据；probe allowlist 同枚举），仅对 allowlist 内 namespace 执行展平 + 恢复 + 形状校验 400；**其余一切 namespace（含全部 `mcp__*`）原字节精确透传**，不入恢复表、不因它们的形状 400。
  2. 碰撞/唯一性校验与 400 范围同步收窄为：平铺 function/custom + allowlist 子函数名；顶层未知 tool shape 的保守 400 保留（防误路由）；非 allowlist namespace 的内部形状不再触发 400。
  3. 测试范围同步：非 allowlist namespace 请求/响应字节级 no-op 成为显式断言（含 `mcp__*` wrapper 与其中 function 的原样保留）。
  4. 验证点：计划已有的 targeted Kimi fresh parent/child re-verify 即窄方案的 first gate——若 mixed-shape 下模型行为异常，保留失败证据回 controller 裁决，而不是预先放宽到全量展平。
- **修复风险（低）**: 两处文本边界（适配集合、400/测试范围）收窄，不触动已证实的请求/响应机制与验证阶梯。
- **严重程度（高）**: 涉及 live route 可用性、未验证前提与 binding scope，且是 controller 明确要求裁决的中心设计问题。

### 2-未修复-中-计划将响应兼容实现禁令错误归因于用户，并把非 stateful 设计误称为 stateful stream rewrite

- **位置**: 「响应的最小恢复设计」末段：“用户明确要求本轮不实现 stateful stream rewrite，故这里仅给设计，代码仍未改。”（对照「当前交付和阻塞」中“等待 controller plan check/适用审核”）。
- **问题类型**: 契约缺失 / 归因错误（约束来源失真）。
- **当前写法**: 把“本轮不实现”表述为**用户的明确要求**，且用 “stateful stream rewrite” 指代本方案。
- **反例/失败场景**: 实施或复审 Agent（gpt-6-sol、mimo/ds deepreview）读到该句后，认为用户已禁止响应侧改写 → 拒绝实现、要求重新向用户请示，或把本就 request-local 的设计误判为违反用户约束的 “stateful” 机制 → 目标被一个不存在的用户禁令卡死；反之也可能让真实边界（diagnosis delegate 本轮无生产实现授权）失去记录。
- **为什么有问题**: 按 controller 裁决，用户约束针对的是 diagnosis delegate 的实施权限，不是 all-provider 修复目标内必要的 request-local SSE 兼容；本方案明确“仅每 HTTP 请求的一份 immutable map 和有界分帧缓冲”，非跨请求状态。约束来源与机制命名双失真，直接影响实现授权判断。
- **直接证据**: 计划第 89 行原文；计划自身第 69、98、104 行均将实现授权归于 controller plan check/派发（与“用户禁止”自相矛盾）；control.md 对该 bridge 的要求是“explicit minimal design + applicable independent plan review”，非用户禁令；controller focus 归因更正原文。
- **影响**: 实施被错误卡死或错误请示；复审以错误前提否定设计；归因记录与 control 真源不一致。
- **建议改法和验证点**: 将该句更正为：本轮为 diagnosis delegate，按授权边界不实施生产代码；响应侧 request-local SSE 兼容属于 all-provider 修复目标内的必要机制，经本次 plan review 与 controller 裁决后派 `gpt-6-sol` 实现；无跨请求状态/alias。验证点：更正后计划内不再出现把实现禁令归于用户的表述。
- **修复风险（低）**: 单句文本更正。
- **严重程度（中）**: 可能造成真实阻断或复审误判，但不改变技术设计本身。

## Open questions

1. **网关对带 namespace 的历史 `function_call` 的接受度**（计划已自列）：prototype 只有 bare-call rejected history；恢复成功后的下一请求会首次携带 `namespace` 历史。计划的处理（原样保留、targeted re-verify 实测、失败时保留证据再调整）正确；owner = 实现后 targeted Kimi 复验，不需在 plan 阶段解决。
2. **structured `tool_choice` 的 400 边界**：计划可读作（a）structured 指向 allowlist 内裸名才 400，或（b）适配存在时任何 structured 都 400。实测仅 `auto`，Codex 路径未观察到 structured；建议实现取窄读（仅 structured 指向本次恢复表内名称时 400，enum 值原样保留），精确口径交 code review 定稿，不阻塞 plan。
3. **响应中显式冲突 namespace 的失败形态**：计划要求“按明确协议错误失败”但未写机制（终止流的具体可观测形式、是否复用 sanitized 协议错误通道）。约束已明确（不得伪造 completed、不得静默覆盖），机制交 code review；须保证与 oversize/malformed 路径一致的可观测终止。
4. **若 controller 否决 Finding 1、保留宽范围**：必须先补两项证据再实施——(i) Codex 0.167 对 `mcp__*` 恢复调用的注册键形态（公开同版本源码即可），(ii) 碰撞时整请求 400 对该 live route 的可接受性论证。当前无任何一项。
5. **跨请求并发隔离**：计划禁用跨请求状态但未列专门离线测试；建议补一个双请求并发、各自 map 互不污染的断言（防实现引入模块级可变状态），成本极低。

## 最终结论

**fail**（计划需修订后再派实现）。

核心机制经证据检验成立：namespace 参与 0.167 执行契约、request-only 不足、每请求展平+响应恢复的最小方向、SSE/编码/guardian/验证阶梯的必要考虑均已覆盖且与原始 artifacts 一致。阻断点是两个必须先改的计划文本问题——(1) 适配范围须按证据收窄为 `multi_agent_v1` + `collaboration` allowlist、其余 namespace 精确透传（Finding 1，高）；(2) 归因句更正（Finding 2，中）。两处修订均有界、低风险，修订后无需重做本 review 的证据部分，由 controller 裁决确认即可进入 `gpt-6-sol` 实现派发。
