### 已检验并排除的对抗场景（结论摘要）

- **特殊文件/阻塞读**：FIFO、目录、设备在 `resolve → deny → lstat → O_NONBLOCK|O_NOFOLLOW open → fstat` 顺序下均在读前失败；该加固与仓库既有 “without open” 测试模式一致（`test_fifo_denial_is_rejected_without_open`），非过度设计。
- **TOCTOU/叶子替换**：lstat 后替换为 FIFO→`O_NONBLOCK` 不阻塞 + `fstat` 拒绝；替换为符号链接→`O_NOFOLLOW` ELOOP→“cannot read”类；替换为目录→`fstat` 拒绝。运行时原生读取仍在原 deny 策略下进行，plan 的 residual 表已分类“运行期由其它非隔离进程替换”并归调用方。
- **deny 交互**：canonical deny 检查在 open/read 前；`/etc/ssl` 或其别名被 deny（含 deny 扩展带入的祖先）时定位失败而不添加 allow/副本；用户可用显式 `CODEX_CA_CERTIFICATE` 指向获准副本作为补救（plan 文档已写）。
- **相对路径/`~`/空串/空白**：相对路径按 envelope cwd 解析（wrapper 与 runner 均在该 cwd 执行）；字面 `~/ca.pem` 按字面 cwd 路径处理并在文档说明；恰为空串按原生语义落 SSL；空白按字面文件名。均在 plan 测试表有对应用例。
- **HTTP-only 与 Claude 不触达**：helper 以 `urlsplit(route).scheme != "https"` 提前返回且只对 Codex 调用；Claude check/launch 不变。
- **preflight 提前失败**：`--check` 与 launch 共享同一准备，属 goal 期望的“located setup failure”，不是新回归。
- **嵌套/连续调用下 `source` 归因**：wrapper 自动写入的 `CODEX_CA_CERTIFICATE` 在后续嵌套调用中会被当作显式输入（`source=CODEX_CA_CERTIFICATE` 而非 `system-default`），仅影响错误文本归因、不影响选择或安全语义，不构成 finding（未列入 open questions 亦因无行动价值）。
- **goal-bound minimal design / overengineering / overcoupling**：单一行为切片 + 同切片测试/文档；仅新增 1 个常量 + 1 个 helper + 2 处调用点，无新 schema/结果字段/配置面；未改 runner/launcher/preflight/collector/srt adapter/manifest；复用既有 `is_denied`/deny 规范化与既有错误渲染风格；语义所有权位于唯一知晓 route 与子环境的 wrapper 层。未发现 goal drift、scope creep 或结构耦合问题。

- **位置**: plan「Affected files and interfaces」第 3-4 项与「Documentation decision」（“Update both existing envelope sections in S1”）。
- **问题类型**: 范围缺口（文档交付不完整）。

- **反例/失败场景**: 实施后，按 `README.zh.md` 的「## 可选任务禁读边界（macOS）」（172-240 行）操作的调用方得不到任何新信息：不知道 Codex HTTPS 在封装内会自动选择 `/etc/ssl/cert.pem`、不知道 `CODEX_CA_CERTIFICATE`/`SSL_CERT_FILE` 的 precedence 与“恰为空串才回落”“空白即字面路径”的语义、不知道缺失/被拒/无效输入会给出 located setup failure、也不知道 keychain-only 根证书必须显式提供 PEM。中文 README 会继续把“不配置任何 CA 输入”表述为完整用法。

## Open questions

1. **kernel 测试子例 1（automatic default）的“expected bytes”断言未定死。** plan 写“The synthetic native program reads only the effective selected CA path, checks expected bytes from its public fixture …（system public PEM）”。建议实现为测试运行时计算 `/etc/ssl/cert.pem` 的 sha256（或直接读取同一路径字节）经环境变量传给 synthetic native 比对，而**不要**把系统 PEM 字节嵌入测试——该系统包是 OS 维护的 333,483 B / 128 证书文件（本机 sha256 `9dae8d76…`），会随系统更新变化，嵌入即周期性假失败。若只断言路径，也应至少断言 native 收到 `CODEX_CA_CERTIFICATE == /private/etc/ssl/cert.pem` 且该文件在沙箱内可读非空。可行性已核验：kernel fixture 的 `mimo` 路线为 `https://example.com/v1` 会走 https 分支，真实 `codex-agent-run` + `AGENT_TOOLS_FILE` 会经 `command codex` 使用 PATH 中的 synthetic native，全程无需网络。
2. **新文档段落与相邻版本声明的关系。** `README.md:213` 现有“Tested with Codex 0.161.0 …”语句，plan 要求不改动无关版本声明；新的 precedence/空值语义又以 0.162.1 实测为据。建议 CA 段落把版本限定为“as verified on the installed 0.162.1 build”，避免读者误读为全仓库测试版本升级。
