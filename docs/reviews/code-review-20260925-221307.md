### 1-未修复-高-reinstall 在端口冲突时会先停掉旧服务再失败

- **入口/函数**: `codex-auto-review-shim-service install` -> `cmd_install`
- **文件(行号)**: `codex-agent/bin/codex-auto-review-shim-service:73`、`:77`、`:82`、`:86`、`:89`
- **输入场景**: 目标 Mac 已加载同一个 launchd label，但 8788-8793 中有手工 shim 或其他进程监听；用户为恢复另一台 Mac 的 Python 路径重新运行 `install`。
- **实际分支**: `launchctl print` 成功后立即执行 `launchctl bootout`，随后 `lsof` 检出冲突并 `return 1`；写 plist 和 `launchctl bootstrap` 均未执行，也没有恢复旧服务的 rollback。
- **预期行为**: 安装失败时不得削弱现有服务。应在所有可预检条件通过后再切换服务，或者在后续写盘/bootstrap 失败时恢复原 plist 并重新加载原服务。
- **实际行为**: 旧服务被卸载，但旧 plist 仍留在 `~/Library/LaunchAgents`，新 plist 未写入，服务不再运行。README 所称“重新加载已有服务”在该常见冲突路径上不成立。
- **直接证据**: `:73-75` 先执行 `bootout`；`:77-82` 随后检测端口并返回 1。隔离 fixture 复现结果为 `rc=1`、`events=bootout`、`loaded=no`，plist 仍是 `<string>/old-machine/python3</string>`。新增测试 `tests/test_shim_service.py:26-39` 只模拟 `lsof` 无冲突和 bootstrap 成功。README 承诺见 `README.md:267-268`、`README.zh.md:251-252`。
- **影响**: reinstall 的失败路径会把可用服务变成停机状态，且命令只报告端口冲突，不说明旧服务已被卸载；用户若未留意状态变化，自动审批反代会持续不可用。
- **建议改法和验证点**:
  - 先生成并校验候选 plist，识别端口占用者；属于当前 launchd job 的监听不能算冲突，外来监听应在切换前失败。
  - 只有在候选 plist 可原子替换且可 bootstrap 时才 `bootout`；为写盘和 bootstrap 失败提供 trap/rollback，至少恢复旧 plist 并重新 bootstrap。
  - 增加隔离测试：端口冲突、plist 写入失败、bootstrap 失败三种路径都必须断言旧 plist、loaded 状态和进程状态保持或恢复。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-高-端口预检漏掉 8794/8795 且 install 对 crash loop 返回成功

- **入口/函数**: `cmd_install` -> `cmd_status`；实际服务入口 `codex-auto-review-shim.main`
- **文件(行号)**: `codex-agent/bin/codex-auto-review-shim-service:58`、`:77`、`:89`、`:91`、`:109`、`:122`；`codex-agent/shim-routes.json:54`、`:62`；`codex-agent/bin/codex-auto-review-shim:400`、`:435`
- **输入场景**: 8794 或 8795 被其他进程占用，而 8788-8793 空闲；目标机执行 `install` 或 reinstall。
- **实际分支**: `lsof` 只查询 `-iTCP:8788-8793`，因此返回无冲突；plist 写入和 `launchctl bootstrap` 成功。shim 按 routes 顺序绑定，遇到 8794/8795 的 `ThreadingHTTPServer` bind 错误后返回 1；`KeepAlive=true` 使 launchd 反复拉起。`cmd_install` 只等待 1 秒并执行 `cmd_status`，没有检查 job 是否持续运行、目标端口是否全部监听，最后仍以 0 结束。
- **预期行为**: 端口预检必须覆盖 `$ROUTES` 中实际配置的全部 listen 端口；`install` 只有在服务稳定运行且所需 listener 就绪时才能报告加载成功，否则必须非零退出并给出失败端口。
- **实际行为**: `shim-routes.json` 已包含 8794（`mimo-fast`）和 8795（`glm-flash`），但预检范围仍是 8788-8793。若高位端口冲突，命令可能打印“已加载”并返回 0，而 launchd job 已进入 crash loop，冲突端口之后的 route 也无法建立。
- **直接证据**: `codex-agent/shim-routes.json:54`、`:62` 明确声明 8794/8795；服务脚本 `:77`、`:81`、`:119` 三处硬编码只查 8788-8793。`codex-auto-review-shim:435-438` 在任一 bind 失败时返回 1，服务脚本 `:58` 设置 `KeepAlive=true`。只读端口集合验证输出 `unchecked-route-port 8794`、`unchecked-route-port 8795`。
- **影响**: 安装状态与实际可用性不一致；`mimo-fast`/`glm-flash` 静默不可用或全部 route 随 crash loop 抖动，日志与状态也难以区分“已加载”和“正在反复失败”。
- **建议改法和验证点**:
  - 从 `$ROUTES` 解析实际端口集合，动态构造 `lsof` 查询，禁止服务脚本和 route schema 各自维护端口范围。
  - bootstrap 后轮询 `launchctl print` 的 state/pid/last exit code，并验证所有 route 的 listener；超时或退出即失败并停止 KeepAlive crash loop。
  - 增加 8794、8795 单独冲突和 bind 后启动失败测试，断言 `install` 非零退出而不是仅打印 status。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 3-未修复-中-plist 动态路径未做 XML 转义

- **入口/函数**: `plist_body` -> `cmd_install` / `cmd_print_plist`
- **文件(行号)**: `codex-agent/bin/codex-auto-review-shim-service:40`、`:50`、`:51`、`:55`、`:59`、`:86`
- **输入场景**: 目标机 `$HOME` 或解析出的 Python 路径含 XML 元字符，例如 `&`、`<`、`>`；这些在 POSIX 文件名中合法。
- **实际分支**: heredoc 直接把 `$python`、`$SHIM`、`$ROUTES`、`$LOG` 展开到 `<string>` 文本节点，没有 XML escape，也没有写盘后的 `plutil -lint`。
- **预期行为**: plist builder 应生成合法 XML；任何动态路径都需 XML 转义，写入前或原子替换前应验证 plist。
- **实际行为**: 生成物立即变成 malformed plist，bootstrap 失败；若是在 reinstall 中，叠加 Finding 1 后还会先卸载旧服务并覆盖/截断旧 plist。
- **直接证据**: `plist_body` 在 `:50-60` 直接插值。隔离验证使用 `HOME=/private/tmp/code-is-cheap plist&probe` 后，`plutil -lint` 非零退出并报告 `Encountered unknown ampersand-escape sequence at line 9`。新增 fixture `tests/test_shim_service.py:50` 只覆盖带空格路径，没有验证 XML 语义。
- **影响**: 特定合法路径下安装确定失败，并可能使原有 launchd 配置不可恢复；错误来自 plist 解析器，离实际根因较远，排障成本高。
- **建议改法和验证点**:
  - 对所有动态 XML 文本做 `&`、`<`、`>`、引号和控制字符转义，或用系统 plist API/`plutil` 构造结构化 plist。
  - 先写同目录临时文件，执行 `plutil -lint`，再原子 rename。
  - 增加 `&`、`<`、换行路径的 builder 测试和 `plutil -lint` 断言。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

### 4-未修复-中-PYTHONOPTIMIZE 会绕过 Python 3.11+ 探测

- **入口/函数**: `resolve_python`
- **文件(行号)**: `codex-agent/bin/codex-auto-review-shim-service:29`、`:32`、`:70`、`:127`
- **输入场景**: 安装 shell 设置 `PYTHONOPTIMIZE=1`，而 PATH 或 fallback 候选只有 Python 3.9/3.10。
- **实际分支**: Python 优化模式删除 `assert`，版本探测代码继续执行并打印 `sys.executable`；外层只检查输出非空且可执行，于是接受旧解释器。
- **预期行为**: 无论 Python optimize 环境变量如何设置，都必须真实验证 `sys.version_info >= (3, 11)` 并失败关闭。
- **实际行为**: 解释器版本条件不再执行，plist 可写入不符合 README 明示契约的 Python。隔离验证中，`PATH=/usr/bin:/bin PYTHONOPTIMIZE=1` 令 `print-plist` 写出 `/Library/Developer/CommandLineTools/usr/bin/python3`，该解释器实际版本为 3.9.6。
- **直接证据**: `:32` 用 `assert sys.version_info >= (3, 11)` 做控制条件。`PYTHONOPTIMIZE=1 /usr/bin/python3` 下不可能成立的 `assert sys.version_info >= (99, 0)` 仍输出 `assert-skipped 3.9.6`；同一环境下 service 的 `print-plist` 输出该 3.9.6 解释器。文档契约见 `README.md:267-268`、`README.zh.md:251-252`。
- **影响**: Python 解释器探测可能静默降级，后续服务行为不再符合安装文档和测试意图；错误在安装时不可见，直到语法、stdlib 或运行时差异暴露。
- **建议改法和验证点**:
  - 用显式 `if sys.version_info < (3, 11): raise SystemExit`，不要用 `assert` 承担 contract enforcement。
  - 用 `python -I -S` 降低 `PYTHONPATH`/sitecustomize/优化环境影响，并只解析一行结构化输出。
  - 增加 `PYTHONOPTIMIZE=1` + Python 3.9 fallback 的 fixture，断言 `install`/`print-plist` 非零退出且不生成 plist。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中
