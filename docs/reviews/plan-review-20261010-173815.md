## Reviewed Goal And Boundary

Goal Confirmation is present and binding. The work unit must make an existing denied directory containing a dangling old-Python symlink complete setup with controlled missing-target semantics, while preserving recursive denial, valid symlink-target expansion, hardlink/special-file rejection, write restrictions, effective Seatbelt verification, allowed probes, fixed runner execution, and lifecycle/result behavior. ENOENT or `sandbox_check=1` alone must never prove isolation. There must be no ordinary-runner fallback, old-Python installation, business-directory edit, general sandbox redesign, dependency upgrade, or live deployment.

The proposed candidate keeps the canonical missing target in both read/write deny sets, adds its nearest existing directory ancestor as a recursive deny in both sets, verifies every existing deny by effective query plus actual refusal, and only then permits ENOENT for a registered missing target whose exact ancestor has already passed those checks.

## Special Lenses

- **Goal-bound minimal design**: Mostly aligned, but the full resolver and its stricter `..` behavior need proof that they are necessary correctness conditions rather than incidental hardening.
- **Architecture boundary**: The private `load_denies` tuple and per-run `boundary.json` extension stay within the sandbox entry point. No public schema or provider coupling is introduced.
- **Best practice**: Fail-closed error handling and real kernel checks are strong, but a security-sensitive verifier must not use a potentially blocking open for an unclassified node.
- **Optimal solution**: The current runtime's `realpath(strict=ALLOW_MISSING)` is a credible simpler primitive that the plan does not adjudicate.
- **Overengineering**: A complete recursive resolver plus a compatibility story is disproportionate unless the `file/..` divergence is explicitly required and differentially tested.
- **Overcoupling**: Broad ancestor denial necessarily couples missing-link handling to existing input/write boundaries. The plan keeps this in one slice, but diagnostics must preserve the source relationship across those boundaries.

## Findings

### 1-未修复-[高]-自定义完整解析器忽略现有 ALLOW_MISSING 原语并改变既有解析语义
- **位置**: Plan §2 “安装契约为 Python 3.11+”段；§4.1 `_resolve_deny_target` 算法；§7 resolution tests；`resolution-matrix-raw.json`
- **问题类型**: 非最优方案 / 过度设计 / goal drift / 契约缺失
- **当前写法**: Plan 以 `Path.resolve(strict=False)` 会掩盖 EACCES/ENOTDIR 为由，要求实现一个逐组件、递归处理 symlink、`..`、尾 slash 和循环的完整私有 helper；同时说不能假定所有 Python 3.11 都有 `os.path.ALLOW_MISSING`。
- **反例/失败场景**: 当前环境的 `os.path.realpath(path, strict=os.path.ALLOW_MISSING)` 已对缺失叶节点、多个缺失祖先、相对/链式目标和缺失后 `..` 返回完整 canonical path，并传播 PermissionError、ELOOP、ENOTDIR。计划自己的 `resolution-matrix.py` 已记录这组结果。唯一明确差异是 `plain/../good/data`：现有 `Path.resolve(strict=True)` 和 `realpath(ALLOW_MISSING)` 返回 `good/data`，候选 helper 抛 `NotADirectoryError`。若这不是 Goal Confirmation 要求的语义，实施会拒绝当前入口会扩展的有效目标，并把一次局部 dangling-link 修复变成路径解析语义重写。
- **为什么有问题**: Goal 要求保留 valid symlink handling，并明确禁止一般性 resolver/compatibility redesign。Plan 只证明了普通非严格解析有问题，没有证明 `ALLOW_MISSING` 不足，也没有把 `file/..` 的额外严格性提升为已确认 correctness condition。
- **直接证据**: `resolution-matrix-raw.json` 中 `stdlib_allow_missing` 对 `missing-leaf`、`missing-ancestor`、`relative`、`chain`、`after-missing-parent` 成功，对 `loop`、`permission`、`enotdir`、`missing-then-enotdir` fail closed；`enotdir-before-parent` 为 stdlib 成功而 candidate 失败。当前运行时 `posixpath._joinrealpath` 在 `strict=ALLOW_MISSING` 时只忽略 `FileNotFoundError`，其它 OSError 继续传播。Plan line 29 只比较了 `strict=False`，未裁决这一现成原语。
- **影响**: 实施 Agent 可能创建不必要的安全关键解析器、引入兼容分支和新边界语义；合法 target expansion 可能回归，review 也无法确认哪些差异是授权的。
- **建议改法和验证点**: 当前环境优先使用 `os.path.realpath(..., strict=os.path.ALLOW_MISSING)`。若 `file/..` 必须 fail closed，只增加这一最小语义检查，并用 differential tests 明确列出与 stdlib 的所有允许差异。对缺少该 sentinel 的 Python 3.11，明确一个窄兼容策略或 fail-closed runtime error；不要建立一般性 compatibility framework。验证 absolute/relative/chained/missing-parent、EACCES、ENOTDIR、ELOOP，并单列 `plain/../good` 的裁决。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 高

### 2-未修复-[中]-两轮 verifier 对 FIFO/特殊节点和后续 hardlink 没有 fail-closed 类型契约
- **位置**: Plan §4.4 first/second pass；§7 verifier assertions；Goal “hardlink/special-file rejection”与“unsupported or indeterminate resolution/verification fails closed”；`scripts/agent-sandbox:345-356`
- **问题类型**: 状态机漏洞 / 契约缺失 / 测试缺口
- **当前写法**: Plan 验证 manifest 的路径和祖先关系，但没有携带或复核 expected node kind、link count 或 no-follow identity；验证时按 `Path(value).is_dir()` 分流到 `listdir` 或 `open/read`。第二轮仅把 PermissionError/ENOENT 作为通过条件。
- **反例/失败场景**: 一个登记 missing target 在验证前被换成 FIFO 时，`is_dir()` 为假，随后 blocking `open` 可以永久等待，既不返回 ENOENT/ENOTDIR，也不进入计划规定的 fail-closed 路径。若 entry/target 被替换成 symlink、socket、device 或多硬链接 inode，当前写法也没有在操作前稳定拒收；hardlink 的外部别名仍可读取同一 inode。Review-time fresh-FIFO probe 在 macOS/Python 3.11.15 上超过 1 秒仍阻塞，必须终止。
- **为什么有问题**: Goal 明确保留 hardlink/special-file rejection，并要求 indeterminate verification fail closed；单纯依赖外部不修改文件系统的既有 residual risk 不能把无限阻塞变成可接受错误。启动会挂住，runner/lifecycle 状态无法被清晰归因。
- **直接证据**: Current verifier 对每个 string 直接 `Path(value).is_dir()` 后 `os.listdir` 或 `open(...).read(1)`。Plan 的 verifier tests 覆盖 query false、ENOTDIR、ELOOP、other OSError 和 read success，但没有 FIFO/socket/device/hardlink/no-follow case。Setup-side FIFO tests 不能证明 verify-side 状态组合安全。现有 materialization experiment 只创建目录和普通子文件。
- **影响**: setup 可能无定位挂起而不是 exit=1；hardlink/special semantics 被后移或丢失；无法完成“runner 前带上下文拒绝”的验收。
- **建议改法和验证点**: 在 manifest 中保留 load 时的 expected kind，或 verifier 在每次操作前 `lstat`/`fstat` 并只接受预期 regular file 或 directory，明确拒绝 symlink、FIFO、socket、device 和 `st_nlink != 1`。文件读取使用 no-follow/nonblocking open 后再检查 regular type，避免 FIFO 阻塞。增加 verifier mock 与真实 fixture：missing target materialized as FIFO/socket/device/symlink/hardlink 时，1 秒内 fail closed、exec sentinel 未调用、错误含 target/ancestor/source。
- **修复风险（低/中/高）**: 中
- **严重程度（低/中/高/严重）**: 中

### 3-未修复-[中]-祖先扩大后的 required/tool/output/write-root 冲突没有精确来源契约
- **位置**: Plan §3 ancestor decision；§4.3 required inputs/full denies；§7 required-input conflict assertion；`scripts/agent-sandbox:198-202, 385-428, 459-467`
- **问题类型**: 测试缺口 / 契约缺失 / 过度耦合
- **当前写法**: `main` 对每个 missing target 报告新增 ancestor，后续 `require_readable`、output/artifact、write-root/result checks 继续使用完整 deny set；Plan 认为“扩展报告 + 既有冲突错误”足以定位，并只明确要求 required setup input 的无 runner 测试。
- **反例/失败场景**: missing target 落到 `/usr/local`、home 或其它包含 Python、runner、node、launcher、cwd、output parent、result adapter 的最近 existing ancestor 下时，setup 必须 fail closed，但错误通常只显示 `required setup input is denied: <path>` 或 `write directory is denied: <path>`。多个 missing links/ancestors 时，无法从错误本身确定是哪个 link、raw target、ancestor 覆盖了该角色，也无法覆盖 output/canary/artifact/result/write-root 的同类冲突。
- **为什么有问题**: 用户目标特别要求扩大 deny 的副作用和原 required inputs/tool 冲突能够定位失败。Goal 也要求 offending link、target/error context where available。仅仅在更早 stderr 中打印所有 expansions，不等于为后续失败建立了可审计因果关系。
- **直接证据**: `require_readable`/`is_denied` 只接收 path 和 deny strings，不接收 `missing_targets` provenance；plan metadata 已有 declared/link/raw_target/ancestor，却没有定义冲突错误如何引用 covering ancestor。§7 只列 ancestor 包含 required setup input 的一项正向/负向断言。
- **影响**: 实施可能在真实工具冲突时仍出现近似“无定位 startup failure”，review 难以证明副作用已充分披露，多个 missing links 时尤其难诊断。
- **建议改法和验证点**: 将 deny origin mapping 保持到所有冲突检查，错误至少包含 input/output role、conflicting path、covering ancestor、declared entry、offending link、raw/canonical target。增加 multiple missing links、python/node/runner/launcher、prompt/canary、cwd、output parent、artifact、result/write-root collision 的 `--check` 与 launch tests，统一断言无 runner marker 和精确来源。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 中

## Open Questions

1. `plain/../good/data` 的 ENOTDIR fail-closed 是否为 Goal Confirmation 已要求的 path semantics？若否，应保留现有 valid-target 解析行为并删除该额外硬化。
2. 支持矩阵是否必须覆盖没有 `os.path.ALLOW_MISSING` 的 stock Python 3.11？若是，允许的最小 fallback 是什么，如何避免落入一般性兼容框架？
3. 外部并发替换为 FIFO/socket/device/hardlink 是否完全沿用现有 no-snapshot 边界？即使沿用，blocking open 是否仍必须被排除？Finding 2 建议无论答案如何都应 fail closed。
4. 真实 old-python target 的 nearest existing ancestor 及其 required-tool/write-root 冲突未在允许范围内读取业务目录验证；实现 closeout 应在授权的 caller setup 中报告实际 ancestor 和冲突，而不能用 synthetic anchor 代替。

## Conclusion

`fail` as written. The conservative missing-target plus verified-ancestor direction is credible and the retained experiments support its core policy claim, but the plan is not yet code-generation-ready. Before implementation, it should minimize/adjudicate the resolver against `os.path.realpath(strict=ALLOW_MISSING)`, make verifier special-node/hardlink handling nonblocking and fail closed, and bind broad-ancestor conflict failures to exact provenance across required inputs and write boundaries. These changes belong in the same S1 slice and do not require a compatibility framework or broader sandbox redesign.
