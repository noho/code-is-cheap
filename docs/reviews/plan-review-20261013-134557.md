- **当前写法**: plan 只把 `README.md` 列入 affected/allowed files 与文档更新范围（"Update README and the generic sub-agents skill in S-1"），并在证据表声称旧契约位于 `README.md:374-421` 与 `SKILL.md:57-98` 两处。
- **反例/失败场景**: S-1 完成后 README.md 与 skills/sub-agents/SKILL.md 改为 native completion 语义，而 README.zh.md 仍保留"已识别的 Codex 连接重试通知，只有在同一次执行中随后有效完成且所选检查通过后才列为 warnings；未知或未恢复的错误仍属致命错误"及 notice 白名单描述。中文读者/调用方据 zh README 得到的契约与实现相反（以为需要 allowlist、未知错误必致命）；且 plan 的 allowed files 未包含 README.zh.md，实施 agent 按约束无权修正，形成 EN/ZH 语义分叉。
- **为什么有问题**: goal 边界要求随契约更新 "necessary current documentation（README …）"；README.zh.md 是与 README.md 同步维护的双语文档，遗漏使 goal 的文档面只完成一半，且流程约束会阻止顺手修复。

- **建议改法和验证点**: 在 plan 的 affected/allowed files 与 §Documentation decision 中显式加入 `README.zh.md`，要求与 README.md 同步相同语义（native terminal 判定、诊断保留/needs_review、Claude 负向字段拒绝、not_assessed、移除 notice/UUID/attempt 清单与"未知错误致命"表述）；实施后 grep 校验两份 README 与 SKILL.md 不再残留该契约语句。

- **严重程度**: 中

### F2-未修复-中-Claude 诊断帧的硬失败形状规则（system/api_retry、assistant.error 显式 null）缺少真实观测样本，可能引入新的误拒路径（needs-evidence）

- **位置**: plan-v2.md §Valid diagnostics versus structural failure（130-131 行诊断表）；版本 caveat（52 行）；残余风险表（217 行）；`evidence/protocol/claude-sdk-excerpts.txt:1-11,17`；`observed-terminal-fields.json`
- **问题类型**: 契约/验证缺口（证据不足的 hard-error 规则）
- **当前写法**: `system/api_retry` 要求 attempt/max_retries/retry_delay_ms/error/error_status 字段与类型全部成立，"Missing/wrong-type required payload is hard error"；assistant 信封 `error` 的显式 null 或错误类型即 malformed（hard error）。依据仅为 SDK 0.2.138 摘录，而 plan 自己声明该 SDK "not an exact match claim for CLI 2.1.296"。
- **反例/失败场景**: 真实 Claude 调用在 provider 瞬态压力下产生 `system/api_retry` 帧（正是本 work unit 的 motivating 场景）；若 CLI 2.1.296 的该帧相对 SDK 0.2.138 声明存在偏差（如省略 `error_status`、成员类型/数量差异），或 CLI 对未设置 optional 字段输出显式 null（证据文件本身显示 CLI 会输出 `"api_error_status": null`，即存在"未设置也要落 null"的序列化形态），v2 collector 会把一次重试后正常完成的成功调用 hard reject（exit 1 / rejected）——即把要消除的 false-rejection 从文本白名单转移到帧形状上。
- **为什么有问题**: goal 只要求"区分 structurally valid diagnostics 与 malformed frames"，并未要求对未观测帧采取最强 schema 推定；plan 自身原则 "ancillary SDK/CLI metadata is not subjected to a new exhaustive SDK-version gate"（122 行）未延伸到这两类信封；且计划的验证集不覆盖真实 retry/error 帧——S1 回放是已知 Codex 原日志，合成矩阵复刻的是 SDK 形状本身，S6 探针为干净三步成功路径（明示不注入瞬态故障，"Fault classification is covered by synthetic matrices and original replay"）。
- **直接证据**: plan-v2.md:52（版本 caveat）、130-131（规则）、199-204（验证步骤）；claude-sdk-excerpts.txt:1-11（字段清单）、17（error 可选）；observed-terminal-fields.json（CLI 显式 null 序列化实例；两条记录均无 api_retry/assistant.error 实例——observation 包也未记录此类帧）。
- **影响**: 真实调用在故障恢复路径上被误拒（用户可见失败，正是本 work unit 要消除的类别）；或形成"合成样本绿、真实现场红"的验收缺口，归因成本高（只在 provider 瞬态压力时出现）。
- **建议改法和验证点**: 由 controller 在裁决中二选一：(a) 验证优先——在回放/实施阶段读取任一真实捕获的 Claude 帧（或 S6 探针原始流）确认这两类帧的实际形状与 null 序列化，把结论记录为 protocol decision 后再冻结规则；(b) 策略降级——对 mid-stream 诊断帧的 payload 形状偏差（api_retry 字段、assistant.error 显式 null）以有界 anomaly 记录（needs_review、保留证据），仅对非诊断的结构损坏维持 hard error，与 plan 自身"ancillary metadata 不做新版 SDK gate"的原则一致。若维持 hard error，应在残余风险中显式列出"未观测帧形状 hard reject"并给出 owner/destination。验证点：补两条合成用例（api_retry 缺 error_status、assistant error:null）并注明期望来源为协议决策而非观测事实。
- **修复风险**: 低（局部规则调整或一次验证读取）
- **状态**: needs-evidence（待 controller 裁决）
