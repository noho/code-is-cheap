## Findings

### 1-未修复-低-Claude 中间 assistant 文本不得替代 final 的主变更未被显式回归覆盖
- **位置**: plan-v2.md 行为矩阵 row 60（"Missing/empty/nontext final… Test nested-only Claude text cannot become final"）；对照 plan-v2.md:33 与 `scripts/agent-run-result.py:401–403`
- **问题类型**: 测试缺口
- **当前写法**: row 60 显式点名的 final 归属用例只有 "nested-only Claude text cannot become final"；缺失/空/nontext final 场景只以 "no fabricated final" 概括。
- **反例/失败场景**: nested-only 文本在当前代码就不会成为 final（`:335–337,401` 仅 root 写入），该点名用例在旧实现上也通过。真正的行为变化是：result 缺失/空/nontext 时，`:401–403` 滚动写入的 root assistant 文本会被当作 `final_answer` 返回。实现者若保留该滚动逻辑、只挡 nested 文本，再写一个不含 assistant 文本的 missing-final fixture，全部点名测试仍绿，但截断流会把中间 assistant 文本当正常 final 返回。
- **为什么有问题**: 违反 row 33 的结构化来源（"Claude's unique root result string…not a substitute final"、"no replacement final prose"）和 SKILL.md 已文档化的 "唯一根 result 拥有最终答复"；调用方会把中间文本当作正常 final 接受——正是本工作单元要消除的误导性输出。
- **直接证据**: `agent-run-result.py:344–347`（result 写 final）、`:401–403`（root assistant 文本写 final，result 缺失时残留）；`SKILL.md` final 段落；plan-v2.md:33、row 60。
- **影响**: final 归属契约的核心变更点缺少验证锚；回归形同虚设时误导性 final 会进入调用方。
- **建议改法和验证点**: 在 row 60 显式增加一条断言：含 root assistant 文本但 result 缺失/空/nontext 的 Claude 流 → `final_answer` 按 row 24 规则为 null 或观测空串，中间文本仅在 retained logs 可见，且断言 `final_answer` 不等于该 assistant 文本。
- **修复风险（低）**: 低
- **严重程度（低）**: 低

## Focus-area verdicts

- **Pre-exec error handoff (row 43)**: **necessary and minimal.** Setup/native collision is real (assumption 6); matrix row 63 requires distinguishing setup failure from an actual CLI returning the identical number, which reserved exit numbers and log-guessing cannot do (both excluded by the binding text). The plan drops the old plan's general launch/outcome channel and keeps an invocation-local, error-only pipe that closes on successful native exec and is not exposed to Agent tools. The residual discipline — every launcher/helper failure path writes the handoff, terminal exec reports exec failure — is stated ("launcher/helper setup errors report their cause", "terminal exec") and exercised via real repository paths (row 63). No finding.
- **Primary-delivery exception (row 46)**: **necessary and minimal.** goal.md:10 explicitly requires the plan to spell out wrapper I/O/collection failure visibility; "expose that genuine execution/delivery failure plainly" (amendment) forbids both silent success (outer 0) and a wrapper-status taxonomy. Outer 1 for native 0 + stderr facts, native nonzero preserved exactly, report-presence as the delivery signal — coherent and within mandate. No finding.
- **Aux copy cannot override native 0 + final**: fixed exactly at row 45/61 (collected and detail modes, including missing/stale/mismatch/cleanup; primary final unchanged; temp path retained). Verified against the promotion sites in assumption 4.
- **No-clobber**: preserved (rows 45/65; assumption 10), including the post-run race re-check and "destination never clobbered" even when the copy fails.
- **Parser final attribution**: contract text is correct and structural (assumption 7). One test-precision gap → Finding 1.
- **Migration / long-final tests**: covered — row 58 asserts decoded full-fixture equality (Unicode, newlines, edge whitespace) through collector and both runners plus removed fields absent; row 67 migrates helpers off `validation_status` exits and requires independent assertions of schema keys, exact process code, exact final and diagnostic source. Sufficient.

## Open questions

Clarify whether the field admits null (recommended) or whether that case emits no report at all. Nonblocking: the narrative already forbids fabrication; resolve at implementation/code review.
2. **Handoff activation contract.** The plan bounds launcher changes to "this error boundary and terminal exec, preserving ordinary interactive behavior" but leaves the activation mechanism (how the runner passes the descriptor) to the implementer. Confirm at code review that launcher invocation without the handoff is behavior-identical to today.
