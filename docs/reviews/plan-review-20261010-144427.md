## 分项评估（按评审焦点）

- **最小目标对齐**: 11 条决策逐条可映射 goal 的 confirmed behavior / success signals，未发现 goal drift、新增验收标准或 future-slice work。两处小收口（runner whitespace/regular-file 校验；显式 label 字符集与 `.`/`..` 排除）落在 goal 已确认的 “plain nonempty task” 与既有文件名安全语义内，非新目标。无未批准的 hardening / migration（兼容性移除是 goal 明示的范围裁剪）。

- **可实施契约**: 未发现迫使实现者重新设计的缺口；关键落点（prompt 追加点、canary 开关点、label/identity 派生点、SECONDS 取值点、adapter 参数、agent-sandbox 交互）均已定位到现有代码结构。
- **失败路径**: setup-before-launch、opt-in 时的 mismatch/missing fail-closed 拒收、metrics 缺失→null（不制造成功）均保留/明确；被移除护栏的净暴露见 Finding 1（低，fail-closed）。

## Findings

### 1-未修复-低-opt-in canary 开放 CANARY 讨论后，含无关独立 CANARY 字面量的任务/产物存在 fail-closed 误拒路径，且该输入约束未在计划中定义

- **位置**: plan 决策 4（"All three task sources accept natural language, including discussion of CANARY …; remove heading and broad stale-token regex checks"）与决策 5（"Does not scan unrelated task text for historical canary syntax; actual current proof mismatch is still enforced when opt-in"）；执行面在 `scripts/agent-run-result.py` 的 `reported_tokens`/`check_proofs`（:269-305）。文档落点应为决策 9 的 `references/advanced.md` 与 README opt-in 小节。
- **问题类型**: 契约缺失（opt-in 路径的输入约束未定义/未文档化）。
- **当前写法**: D4 明确允许任务正文讨论 CANARY；D5 明确不对任务正文做历史 token 扫描，但保留结果期 proof 强制；计划未说明“启用 --canary 时任务/声明产物中不得出现其他独立 `CANARY[:=]` 行”。
- **反例/失败场景**: 一个 `--canary` 验证派发，任务正文或 `--artifact` 要求的新报告中出现独立的 `CANARY=<旧值>` 行（例如要求子 Agent 对比新旧 token 格式、或报告里引用旧协议样例——本仓库文档正大量讨论 canary）。子 Agent 按任务把该行写进最终答复或新产物；adapter 将其计为 proof 并与本轮 token 比对 → `canary_status=mismatch` → `validation_status=rejected`、runner exit 1。任务被正确完成却整单拒收。
- **为什么有问题**: 旧 preflight 护栏（正文任何位置出现 `CANARY=…` 即 setup 失败，sub-agent-preflight:263-280）此前使该组合不可达；D4 移除护栏、D5 保留结果期强制，但计划没有定义/文档化替代约束，也没有相应验证项——实现者可能不复现该交互，文档读者会在 opt-in 路径上踩坑。
- **直接证据**: plan D4/D5 原文；`scripts/sub-agent-preflight`:263-280（旧护栏）；`scripts/agent-run-result.py`:269-305（最终答复与每个 artifact 内的独立 CANARY 行逐条比对，不匹配记 error → rejected）；`tests/test_agent_run_results.py`:150-162、:211-221（现有行为测试证明 artifact 也参与比对，含行号定位）。
- **影响**: opt-in 验证派发被误拒 + 返工重派（fail-closed：不会错误放行，无数据损坏；错误信息含路径/行号，可诊断）。
- **建议改法和验证点**: 在 advanced.md 的 canary 小节与 README opt-in 说明中写清输入约束：启用 `--canary` 的任务正文与声明产物中，除本轮证明行外不得出现其他独立 `CANARY[:=]` 行（或让该行置于围栏/缩进样例内）。可选补充（如 controller 认为仍在本 slice 的 diagnostic 定位内）：`--canary` 时对任务正文中独立 CANARY 字面量输出 warning（非 failure、不改 exit code），与 goal “optional early setup/diagnostic convenience” 一致。验证点：S1 文档核对项确认该约束已写明；无需新增执行路径。
- **修复风险（低/中/高）**: 低（一条文档说明；无代码/契约/schema 变更；若加 warning 亦为既有 exit 语义内的增量）。
- **严重程度（低/中/高/严重）**: 低。
