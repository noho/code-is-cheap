## Reviewed target and scope

计划目标是用五份用户提供的官方 catalog（DeepSeek/GLM/Kimi/MiMo/Qwen）替换八个云 profile 的
GPT 派生 session 条目，保持 endpoint/key 覆盖、原生 GPT/business/local 行为、lifecycle/stats/result
与 read/write/network/approval 边界。审查重点：goal 对齐与最小性、catalog 映射与真实文件一致性、
Lite/tool-mode/guardian 传输语义、code-mode host 与沙箱边界、max/窗口行为、安装完整性与回滚、
测试与独立合成验证的可实施性，以及是否引入未授权机制或未证实声明。

计划的事实基础在本次独立复核中基本全部成立（见下表）。未发现 blocker；两条低严重度 finding

## Findings

### 1-未修复-低-README.zh.md 不在计划范围内，中文文档会与部署事实脱节
- **位置**: plan.md §Allowed files/modules L129（"Root `README.md`"）与 §Documentation L235。
- **问题类型**: 契约缺失 / 文档缺口。
- **当前写法**: 文档更新与 allowed files 只列 Root README.md；全文未出现 README.zh.md。
- **反例/失败场景**: 实现按计划完成后，`README.zh.md:422` 仍写 `| kimi | kimi-k3 |`，
  L461-466 仍描述"九个第三方 catalog 由 Codex 内置目录（`codex debug models`）现场生成：修正 guardian 工具模式、
  给各模型补入卡片窗口和 direct 工具模式、会话模板按工具能力选择"，与转换后的官方 catalog、
  Kimi 逻辑名 `k3`、GLM Flash 派生条目、Qwen 预算等事实相反。中文读者会得到错误的模型名与生成机制说明。
- **为什么有问题**: 仓库惯例是两份 README 同提交同步维护（最近 8 次涉及 README 的提交均同时修改两文件）；
  goal.md 要求"Update the relevant README and meaningful tests"，G5 要求文档与测试/事实一致。
- **直接证据**: plan.md L129/L235 仅列 README.md；README.zh.md L422、L453-466 与 README.md L459、L489-506 为同一段落的双语版本；`git log -- README.zh.md` 与 `-- README.md` 显示成对更新。
- **影响**: 用户可见文档与真实部署不一致；PR review 可能以"文档未同步"退回，产生返工。
- **建议改法和验证点**: 将 README.zh.md 加入 allowed files 与 L235 更新范围，同步更新 profile 表
  （kimi 逻辑名 k3 与 wire 分离、GLM Flash 派生标注、qwen 预算、MiMo host/CodeMode/Lite 前提、
  五个跟踪源快照与"生成型产物不入库"的新表述）。验证点：两 README 对应段落数字/名称一致。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

### 2-未修复-低-`code_mode_host` 默认已为 true，计划未记录该事实，负例设计可能失效
- **位置**: plan.md L106（三张 MiMo 卡加 `[features] code_mode_host=true`）、L108（agent-sandbox host handoff）、
  L199（"With host false, the Code Mode call produces a visible unavailable-host failure …"）。
- **问题类型**: 测试缺口 / 验证前提未实证。
- **当前写法**: 计划把 `features.code_mode_host=true` 当作 MiMo Code Mode 可用的"actual additional requirement"
  写进卡片、composer overlay 与 sandbox handoff，并计划在 "host false" 时验证 unavailable-host 失败。
- **反例/失败场景**: 实现者以"未设置 = host false"构造负例（fixture 省略该键）。但 0.162.1 上该 feature
  stage 为 stable、有效默认值为 true：负例实际在 host=true 下运行，会观察到正常执行，
  可能据此误判机制、弱化或删除该断言；也可能误以为卡片/composer 改动才是"启用 host"的开关，
  对三处显式置 true 的必要性（相对默认值）作出错误归因。
- **为什么有问题**: 负例只有在显式 `code_mode_host=false` 时才真正覆盖"host 不可用"路径；
  同一事实也说明：在当前 CLI 上，卡片 + composer 单键 overlay + sandbox handoff 是对默认值/机器状态漂移的
  显式保险，而非当前行为的使能条件——计划未说明，实现可能高估其必要性（composer 是共享脚本，改动成本最高）。
- **直接证据**: 本机空 home `codex features list` → `code_mode_host  stable  true`；
  `-c features.code_mode_host=false` → `false`；rust-v0.162.1 `thread_manager.rs`：
  `if config.features.enabled(Feature::CodeModeHost) || config.code_mode.disable_in_process_fallback { ProcessOwned… } else { Disabled… }`；
  `tools/mod.rs` 中 `code_mode_only` 无 availability 回退。
- **影响**: "host 不可用"负例无效或被误删；MiMo 的失败路径未被真实覆盖；对显式配置的收益/成本判断失准。
- **建议改法和验证点**: 在计划（或实现证据）中记录默认值事实；负例 fixture 显式写入
  `[features] code_mode_host=false`（或 `-c features.code_mode_host=false`）并断言可见的 unavailable-host 失败；
  把三处显式置 true 的理由改述为"对默认值/机器状态漂移的显式保险"。
  验证点：fixture 内 `codex features list` 先证明 host=false 的负例环境、再证明 true 的正例环境。
- **修复风险（低/中/高）**: 低
- **严重程度（低/中/高/严重）**: 低

## Open questions

1. `-p <profile>` 分层对嵌套表的合并语义（卡片 `[features]` 与 base `[features]` 是按键合并还是整表替换）
   未获实证：`codex features list` 不接受 `--profile`，`debug prompt-input -p` 在受限网络下触发远端重试未取得结论。
   该差异只在"机器 base 显式设置 code_mode_host=false"或未来默认值变化时才有行为影响；
   建议实现期在 fixture 内用一个可观察 feature 直接验证一次，或在计划中明确以 composer/沙箱两条显式路径为准。
2. Composer 在目标 home 尚无 `[features]` 表时的行为未规定（当前默认 true 使其暂不影响行为；
   若要保持显式 true 的意图，应规定"创建该表"而不是 no-op）。
3. 计划测试条目 "Five tracked byte hashes match the inventory" 中 "the inventory" 指向工作单元文档
   `source-inventory.json` 还是新 `catalog-sources/README.md` 未明确；建议把哈希固定在测试/被测代码内的常量，
   避免测试耦合同一工作单元的 docs 产物（docs/gateflow 属后续 gate 可能调整的内容）。
